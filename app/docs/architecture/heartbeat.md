# Heartbeat scheduler (`make heartbeat`)

(part of Baxter — see [architecture map](../../CLAUDE.md))

Baxter can act on a schedule, unprompted. **`make heartbeat`** runs **one dedicated driver** (`scripts/heartbeat.ts`, a `poll.ts`-style node loop, same image/tokens/config-volume, on the shared network) that every ~minute fires **due tasks** from a shared `~/.mail-agent/schedule/schedule.json` and delivers the result to Discord, email, or SMS (a phone number, or a previously received SMS group via `sms-cli send-group`). From normal email/Discord runs, Baxter controls ordinary tasks via **`schedule-cli`** (`add`/`cancel`/`list`, plus the read-only `groups` discovery verb for SMS-group targets) and runtime-owned tasks via `schedule-cli system list`, `schedule-cli system enable <key>`, `schedule-cli system disable <key>`, and `schedule-cli system trigger <key>`; system tasks cannot be added or their recurring records cancelled. The shim + `Bash(schedule-cli *)` grant ride the email/Discord grant sets (so a voice-dispatched run, which reuses `DISCORD_TOOLS`, has it too); a heartbeat-fired run is deliberately **not** granted `schedule-cli` (a scheduled task can't modify tasks). The surfaces' tool allow-lists differ (mail: mail + schedule-cli; discord: discord + schedule-cli — reused as-is by voice-dispatch; heartbeat: mail + discord + sms, but *not* schedule-cli) — and rather than hand-synced per-daemon `ALLOWED_TOOLS` strings, they're now **composed from a shared core in `scripts/grants.ts`** (`MAIL_TOOLS`/`DISCORD_TOOLS`/`HEARTBEAT_TOOLS`). **The tool grants stay per-surface (the enforced boundary); the skill docs come from one base list each surface filters.** `grants.ts` defines a single base `SKILL_NAMES`, and each surface's `*_SKILL_NAMES` is `skillNamesExcept(...its exclusions...)` (its `*_SKILL_SRCS` derive from those names): mail excludes `discord`, heartbeat excludes `schedule`, discord/voice exclude nothing. `BAKED_SKILL_NAMES` (the learned-skill shadow-guard floor) is the base list's names (each surface is a subset, so their union is the base). A staged skill *doc* never grants a *tool*: each skill exclusion mirrors a missing tool (heartbeat has neither the `schedule` doc nor `schedule-cli`; mail neither `discord` doc nor `discord-cli`), and the fail-closed `HEARTBEAT_TOOLS` (no `schedule-cli`), not the doc absence, is what actually prevents a scheduled task from scheduling. So the "keep the allow-rule sources in sync" hazard is gone: one tool source of truth per surface, one base skill list, and the guard can't drift from what the daemons stage.

- **Proactive date follow-ups:** admitted Mail/SMS/Home Chat turns may add an ordinary one-shot through `followup-cli`. It uses an existing scheduler delivery route and follows the ordinary heartbeat prompt, delivery, retry, give-up, and cancellation paths. See [proactive follow-ups](proactive-followups.md).
- **`scripts/schedule-store.ts`** — the store: pure queue helpers (`selectDue`, `applyClaim`→task|null, `applyOnSuccess`/`applyOnFailure`, `resolveNextRun` via `cron-parser` + an `Intl` wall-time-in-zone conversion, `cronMinGapMinutes`) **plus** locked/atomic I/O (`mutate` = `proper-lockfile` + temp-file `rename`; the lock is held only for the brief read-modify-write, never across a fire) and the log helpers. `envInt` fails **closed** on a bad numeric env var.
- **Queue semantics (SQS-style):** due = `next_run_at ≤ now && visible`. Claim sets a **15-min invisibility window** and returns the task or `null` (a concurrent `cancel` wins — the driver fires only a non-null claim). Success removes a one-shot / reschedules a cron; a **hard** failure retries after the window and gives up after `HEARTBEAT_MAX_ATTEMPTS`; an **out-of-tokens** run leaves the claim and pauses the tick (no attempt burned — a global outage isn't the task's fault). Completed, hard-failed, and gave-up outcomes append a line to `task-log.jsonl`; cap deferral emits at most one `skipped` entry per UTC day while other deferred occurrences receive no entry, and out-of-token attempts remain unlogged.
- **Enforced limits (code, not prompt):** min 1-hour recurrence for `--cron` (validated over the next 100 occurrences, no wall-clock cap; one-shot `--at` any time), `HEARTBEAT_MAX_TASKS`, and a daily `HEARTBEAT_MAX_FIRES_PER_DAY` cap enforced by the durable agent-run quota reservation below (not by counting log lines). These bound the persistence a prompt-injected `schedule-cli add` could otherwise turn into unbounded autonomous runs.
- **System tasks (runtime-owned):** the compile-time registry (`scripts/system-tasks.ts`, `SYSTEM_TASKS`) has one canonical ranged task, `morning-check-in`, at `system:morning-check-in`. Its cron anchors eligible days; each new occurrence persists one random household-local minute from 08:00–08:59. Reconciliation chooses that minute only on creation, enable, repair, expiry, completion, or final give-up; claims and nonfinal retries preserve it. A selected run catches up strictly before noon on its civil date and is expired without dispatch at noon or later. `schedule-cli system enable|disable morning-check-in` controls the canonical task, while `system trigger morning-check-in` creates an independent due-now ordinary-id one-shot that neither uses the range/cutoff nor mutates the canonical occurrence. Startup and every reconciliation delete only proved exact retired canonical key/id pairs before validation; uncertain retired collisions remain fail-closed with the existing operator-repair diagnostic. The reconciliation gate runs before every due selection, creates/repairs the canonical record in one transaction, and fails closed for every other reserved-id or mixed-key collision.
- **Agent-run quota (`fire-quota.json`):** the daily `HEARTBEAT_MAX_FIRES_PER_DAY` cap is a durable UTC-date reservation file beside `schedule.json` (its own lock — reservation never runs inside a store transaction). First use seeds the window once from today's legacy log fires; after that only the reservation state counts, and UTC-day rollovers reset it empty without re-seeding. Every actual model invocation reserves its own slot immediately before that invocation, bound to the firing task's id. Ordinary prompted fires still defer the occurrence when denied. The runtime-owned morning check-in instead uses deterministic per-contact fallback: quota denial stops later reservation attempts for that invocation but completes one delivery chain for every snapshotted contact. Out-of-tokens releases that contact's slot and has the same stop-and-fallback behavior. Fires that never touch a model (including a no-event digest and a zero-recipient check-in) never reserve. Log entries carry an audit-only `agent_run` flag (and `system_key` for system fires).
- **Natural morning handoff:** during the half-open `[06:00, 12:00)` household-local window, accepted direct mail/1:1 SMS can close that person's canonical recurring morning occurrence across admitted aliases; Home Chat and an admitted SMS group close the shared household occurrence. Inbound consumption is persisted after durable admission but before context preparation or dispatch, and is never rolled back: a contact previously consumed directly or automatically cannot win again, while distinct direct contacts may each consume once; a shared winner closes the occurrence, and any earlier direct or automatic token makes a later shared close context-ineligible (silent). Unsafe, incomplete, ambiguous, or outsider SMS-group metadata still closes an admitted group silently, with no morning context. A winning reply folds any eligible addition into its one normal inbound response rather than sending a separate morning message.

  The separate `morning-handoff.json` sidecar is best-effort suppression state, not schedule authority. Heartbeat inspects it before calendar/model/provider work, filters earlier winners, then performs a final automatic consume immediately before each SMS-first/email-fallback provider chain; that winner may finish its fallback chain while a later shared close suppresses only contacts not yet finally consumed. Inbound closure does not advance the schedule: normal heartbeat processing advances the selected occurrence. Sidecar failure and cross-process races deliberately fail toward skipped automatic delivery rather than claiming strict cross-process atomicity. Manual `schedule-cli system trigger morning-check-in` one-shots remain independent and never read or write handoff state.
- **Morning check-in behavior:** the handler refreshes/selects calendar data first. calendar-first precedence means a qualifying event selects calendar copy on every weekday; only an empty Friday may use one title-only weekend hint, an empty Monday gets the weekly check-in, and other empty days do no recipient, knowledge, reservation, model, or provider work. Generic subjects exclude private calendar and durable-knowledge fields; attribution-safe durable knowledge may inform a recipient's body. Friday prompts/fallbacks receive no itinerary fields, and Friday runtime validation rejects the protected selected/unselected titles, complete and standalone clock/day/date/all-day phrases, and locations (including short normalized values) from generated subject/body. The noon cutoff gates dispatch only: a handler claimed before noon may finish and advance after noon. Sending modes retain one content-suppressed tool-less generation and SMS-first/same-contact-email fallback per contact, bounded fallbacks, cleaned greetings, and aggregate-only diagnostics.
- **Timezone** is the requester's: Baxter sets `--tz` from what they state/known, asking if a clock-time task needs it; `HEARTBEAT_TZ` is only the fallback. The driver writes `DISCORD_TOKEN_PATH` (0600) at startup like `discord-bot.ts` and strips the token from fired runs' env.
