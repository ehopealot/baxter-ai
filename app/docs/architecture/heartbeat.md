# Heartbeat scheduler (`make heartbeat`)

(part of Baxter — see [architecture map](../../CLAUDE.md))

Baxter can act on a schedule, unprompted. **`make heartbeat`** runs **one dedicated driver** (`scripts/heartbeat.ts`, a `poll.ts`-style node loop, same image/tokens/config-volume, on the shared network) that every ~minute fires **due tasks** from a shared `~/.mail-agent/schedule/schedule.json` and delivers the result to Discord, email, or SMS (a phone number, or a previously received SMS group via `sms-cli send-group`). Baxter only *edits* the schedule via **`schedule-cli`** (`add`/`cancel`/`list`, plus the read-only `groups` discovery verb for SMS-group targets) from his normal email/Discord runs — the shim + `Bash(schedule-cli *)` grant ride the email/Discord grant sets (so a voice-dispatched run, which reuses `DISCORD_TOOLS`, has it too); a heartbeat-fired run is deliberately **not** granted `schedule-cli` (a scheduled task can't schedule or cancel tasks). The surfaces' tool allow-lists differ (mail: mail + schedule-cli; discord: discord + schedule-cli — reused as-is by voice-dispatch; heartbeat: mail + discord + sms, but *not* schedule-cli) — and rather than hand-synced per-daemon `ALLOWED_TOOLS` strings, they're now **composed from a shared core in `scripts/grants.ts`** (`MAIL_TOOLS`/`DISCORD_TOOLS`/`HEARTBEAT_TOOLS`). **The tool grants stay per-surface (the enforced boundary); the skill docs come from one base list each surface filters.** `grants.ts` defines a single base `SKILL_NAMES`, and each surface's `*_SKILL_NAMES` is `skillNamesExcept(...its exclusions...)` (its `*_SKILL_SRCS` derive from those names): mail excludes `discord`, heartbeat excludes `schedule`, discord/voice exclude nothing. `BAKED_SKILL_NAMES` (the learned-skill shadow-guard floor) is the base list's names (each surface is a subset, so their union is the base). A staged skill *doc* never grants a *tool*: each skill exclusion mirrors a missing tool (heartbeat has neither the `schedule` doc nor `schedule-cli`; mail neither `discord` doc nor `discord-cli`), and the fail-closed `HEARTBEAT_TOOLS` (no `schedule-cli`), not the doc absence, is what actually prevents a scheduled task from scheduling. So the "keep the allow-rule sources in sync" hazard is gone: one tool source of truth per surface, one base skill list, and the guard can't drift from what the daemons stage.

- **`scripts/schedule-store.ts`** — the store: pure queue helpers (`selectDue`, `applyClaim`→task|null, `applyOnSuccess`/`applyOnFailure`, `resolveNextRun` via `cron-parser` + an `Intl` wall-time-in-zone conversion, `cronMinGapMinutes`) **plus** locked/atomic I/O (`mutate` = `proper-lockfile` + temp-file `rename`; the lock is held only for the brief read-modify-write, never across a fire) and the log helpers. `envInt` fails **closed** on a bad numeric env var.
- **Queue semantics (SQS-style):** due = `next_run_at ≤ now && visible`. Claim sets a **15-min invisibility window** and returns the task or `null` (a concurrent `cancel` wins — the driver fires only a non-null claim). Success removes a one-shot / reschedules a cron; a **hard** failure retries after the window and gives up after `HEARTBEAT_MAX_ATTEMPTS`; an **out-of-tokens** run leaves the claim and pauses the tick (no attempt burned — a global outage isn't the task's fault). Every fire appends one line to `task-log.jsonl` (`completed|failed|gave-up|skipped`).
- **Enforced limits (code, not prompt):** min 1-hour recurrence for `--cron` (validated over the next 100 occurrences, no wall-clock cap; one-shot `--at` any time), `HEARTBEAT_MAX_TASKS`, and a daily `HEARTBEAT_MAX_FIRES_PER_DAY` cap the driver derives from today's (UTC) log lines (durable across restart). These bound the persistence a prompt-injected `schedule-cli add` could otherwise turn into unbounded autonomous runs.
- **Timezone** is the requester's: Baxter sets `--tz` from what they state/known, asking if a clock-time task needs it; `HEARTBEAT_TZ` is only the fallback. The driver writes `DISCORD_TOKEN_PATH` (0600) at startup like `discord-bot.ts` and strips the token from fired runs' env.
