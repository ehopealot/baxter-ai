# Heartbeat scheduler (`make heartbeat`)

(part of Baxter — see [architecture map](../../CLAUDE.md))

Baxter can act on a schedule, unprompted. **`make heartbeat`** runs **one dedicated driver** (`scripts/heartbeat.ts`, a `poll.ts`-style node loop, same image/tokens/config-volume, on the shared network) that every ~minute fires **due tasks** from a shared `~/.mail-agent/schedule/schedule.json` and delivers the result to Discord, email, or SMS (a phone number, or a previously received SMS group via `sms-cli send-group`). From normal email/Discord runs, Baxter controls ordinary tasks via **`schedule-cli`** (`add`/`cancel`/`list`, plus the read-only `groups` discovery verb for SMS-group targets) and runtime-owned tasks via `schedule-cli system list`, `schedule-cli system enable <key>`, `schedule-cli system disable <key>`, and `schedule-cli system trigger <key>`; system tasks cannot be added or their recurring records cancelled. The shim + `Bash(schedule-cli *)` grant ride the email/Discord grant sets; a heartbeat-fired run is deliberately **not** granted `schedule-cli` (a scheduled task can't modify tasks). The surfaces' tool allow-lists differ (mail: mail + schedule-cli; discord: discord + schedule-cli; heartbeat: mail + discord + sms, but *not* schedule-cli) — and rather than hand-synced per-daemon `ALLOWED_TOOLS` strings, they're now **composed from a shared core in `scripts/grants.ts`** (`MAIL_TOOLS`/`DISCORD_TOOLS`/`HEARTBEAT_TOOLS`). **The tool grants stay per-surface (the enforced boundary); the skill docs come from one base list each surface filters.** `grants.ts` defines a single base `SKILL_NAMES`, and each surface's `*_SKILL_NAMES` is `skillNamesExcept(...its exclusions...)` (its `*_SKILL_SRCS` derive from those names): mail excludes `discord`, heartbeat excludes `schedule`, discord excludes nothing. `BAKED_SKILL_NAMES` (the learned-skill shadow-guard floor) is the base list's names (each surface is a subset, so their union is the base). A staged skill *doc* never grants a *tool*: each skill exclusion mirrors a missing tool (heartbeat has neither the `schedule` doc nor `schedule-cli`; mail neither `discord` doc nor `discord-cli`), and the fail-closed `HEARTBEAT_TOOLS` (no `schedule-cli`), not the doc absence, is what actually prevents a scheduled task from scheduling. So the "keep the allow-rule sources in sync" hazard is gone: one tool source of truth per surface, one base skill list, and the guard can't drift from what the daemons stage.

- **`scripts/schedule-store.ts`** — the store: pure queue helpers (`selectDue`, `applyClaim`→task|null, `applyOnSuccess`/`applyOnFailure`, `resolveNextRun` via `cron-parser` + an `Intl` wall-time-in-zone conversion, `cronMinGapMinutes`) **plus** locked/atomic I/O (`mutate` = `proper-lockfile` + temp-file `rename`; the lock is held only for the brief read-modify-write, never across a fire) and the log helpers. `envInt` fails **closed** on a bad numeric env var.
- **Queue semantics (SQS-style):** due = `next_run_at ≤ now && visible`. Claim sets a **15-min invisibility window** and returns the task or `null` (a concurrent `cancel` wins — the driver fires only a non-null claim). Success removes a one-shot / reschedules a cron; a **hard** failure retries after the window and gives up after `HEARTBEAT_MAX_ATTEMPTS`; an **out-of-tokens** run leaves the claim and pauses the tick (no attempt burned — a global outage isn't the task's fault). Completed, hard-failed, and gave-up outcomes append a line to `task-log.jsonl`; cap deferral emits at most one `skipped` entry per UTC day while other deferred occurrences receive no entry, and out-of-token attempts remain unlogged.
- **Enforced limits (code, not prompt):** min 1-hour recurrence for `--cron` (validated over the next 100 occurrences, no wall-clock cap; one-shot `--at` any time), `HEARTBEAT_MAX_TASKS`, and a daily `HEARTBEAT_MAX_FIRES_PER_DAY` cap enforced by the durable agent-run quota reservation below (not by counting log lines). These bound the persistence a prompt-injected `schedule-cli add` could otherwise turn into unbounded autonomous runs.
- **System tasks (runtime-owned):** the compile-time registry (`scripts/system-tasks.ts`, `SYSTEM_TASKS`) has one canonical ranged task, `morning-check-in`, at `system:morning-check-in`. Its cron anchors eligible days; each new occurrence persists one random household-local minute from 08:00–08:59. Reconciliation chooses that minute only on creation, enable, repair, expiry, completion, or final give-up; claims and nonfinal retries preserve it. A selected run catches up strictly before noon on its civil date and is expired without dispatch at noon or later. `schedule-cli system enable|disable morning-check-in` controls the canonical task, while `system trigger morning-check-in` creates an independent due-now ordinary-id one-shot that neither uses the range/cutoff nor mutates the canonical occurrence. Startup and every reconciliation delete only proved exact retired canonical key/id pairs before validation; uncertain retired collisions remain fail-closed with the existing operator-repair diagnostic. The reconciliation gate runs before every due selection, creates/repairs the canonical record in one transaction, and fails closed for every other reserved-id or mixed-key collision.
- **Agent-run quota (`fire-quota.json`):** the daily `HEARTBEAT_MAX_FIRES_PER_DAY` cap is a durable UTC-date reservation file beside `schedule.json` (its own lock — reservation never runs inside a store transaction). First use seeds the window once from today's legacy log fires; after that only the reservation state counts, and UTC-day rollovers reset it empty without re-seeding. Every actual model invocation reserves its own slot immediately before that invocation, bound to the firing task's id. Ordinary prompted fires still defer the occurrence when denied. The runtime-owned morning check-in instead uses deterministic per-contact fallback: quota denial stops later reservation attempts for that invocation but completes one delivery chain for every snapshotted contact. Out-of-tokens releases that contact's slot and has the same stop-and-fallback behavior. Fires that never touch a model (including a no-event digest and a zero-recipient check-in) never reserve. Log entries carry an audit-only `agent_run` flag (and `system_key` for system fires).
- **Natural morning handoff:** during the half-open `[06:00, 12:00)` household-local window, accepted direct mail/1:1 SMS consumes one resolved person's complete alias set before prompt preparation or dispatch. That includes an unambiguously associated sender-only email alias, but never uses it as an automatic email target. A consumed person cannot win again through another SMS/email alias; distinct people can each win once. **Home Chat is never a handoff surface:** it does not inspect, claim, close, or render `morning-handoff.json` state.

  An inbound SMS group is admitted only when its strict id, sender, and complete participant snapshot are household-safe. Every non-Baxter participant must map to exactly one resolved contact; the group atomically consumes only those covered contacts' full alias sets, and its reply audience contains only those contacts. It does not globally close email-only or absent contacts. Unsafe, ambiguous, incomplete, malformed, corrupt, or outsider group state is a no-op for handoff state and context. Before a group run starts, a later unsafe **or changed** participant/contact fingerprint invalidates a pending claim; the captured snapshot is also re-evaluated against the freshly loaded allowlist and resolved roster, so it cannot attach to a changed audience. A winning reply folds any eligible addition into its one normal inbound response rather than sending a separate morning message.

  A canonical **automatic** morning group update has a stricter full-audience requirement: the newest valid inbound group snapshot from the last 24 hours must cover every currently pending resolved contact. Its last appended inbound snapshot is authoritative; unsafe, incomplete, malformed, or corrupt trailing data never revives an older row, and timestamp ties fail closed. Outbound/direct rows never displace a valid group candidate. If full coverage is absent (including an email-only contact), heartbeat uses the existing per-contact SMS-first/same-contact-email-fallback chains. It fingerprints group id, timestamp, sender, participants, and resolved roster, then reloads/rechecks that fingerprint after generation and after the asynchronous shared-close gate. Any change or a competing direct winner suppresses the prepared group provider call.

  The separate `morning-handoff.json` sidecar is best-effort suppression state, not schedule authority. Heartbeat inspects it before calendar/model/provider work, filters earlier winners, and performs a final automatic consume immediately before each individual provider chain; an admitted winner may finish its same-contact SMS/email fallback while a later shared close suppresses only contacts not yet finally consumed. A fully covered automatic group uses the shared-close gate only after those rechecks. Sidecar failure and cross-process races deliberately fail toward skipped automatic delivery rather than claiming strict cross-process atomicity. Inbound handoff never advances the schedule; normal heartbeat processing advances the selected occurrence. Manual `schedule-cli system trigger morning-check-in` one-shots remain independent and never read or write handoff state.

  **Reminder routing:** ordinary SMS/email/group reminders retain their explicit persisted target. A Home Chat reminder cannot return to the chat: its authenticated author defaults to their resolved direct SMS with a persisted `fallback_email` for that same person's recipient email; if there is no SMS route it uses that email directly. Coalesced Home Chat messages retain a route table keyed by durable message id, so each tagged current message can use only its own authenticated route; every untagged row has a runtime-owned `[history]` prefix and cannot impersonate a route marker. A group is used only when the requester explicitly names one and `schedule-cli groups` yields one unambiguous exact id; it uses the same author's email fallback when available. No display-name guess, recent group, or another household member's address is substituted.

- **Morning check-in behavior:** the handler refreshes/selects calendar data first. calendar-first precedence means a qualifying event selects calendar copy on every weekday; only an empty Friday may use one title-only weekend hint, an empty Monday gets the weekly check-in, and other empty days do no recipient, knowledge, reservation, model, or provider work. On Monday/Friday only, immediately before a direct recipient's delivery, the canonical recurring handler atomically folds and consumes that recipient's still-pending direct one-shot SMS/email reminders due before local noon; it uses their user-facing descriptions only. A manual `system trigger morning-check-in` remains standalone and never folds reminders. Recurring, group, claimed, already-due, and other-day reminders remain normal scheduler work. Generic subjects exclude private calendar and durable-knowledge fields; attribution-safe durable knowledge may inform a recipient's body. Friday prompts/fallbacks receive no itinerary fields, and Friday runtime validation rejects the protected selected/unselected titles, complete and standalone clock/day/date/all-day phrases, and locations (including short normalized values) from generated subject/body. The noon cutoff gates dispatch only: a handler claimed before noon may finish and advance after noon. Sending modes retain one content-suppressed tool-less generation and SMS-first/same-contact-email fallback per contact, bounded fallbacks, cleaned greetings, and aggregate-only diagnostics.
- **Timezone** is the requester's: Baxter sets `--tz` from what they state/known, asking if a clock-time task needs it; `HEARTBEAT_TZ` is only the fallback. The driver writes `DISCORD_TOKEN_PATH` (0600) at startup like `discord-bot.ts` and strips the token from fired runs' env.
