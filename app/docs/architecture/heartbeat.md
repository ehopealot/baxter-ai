# Heartbeat scheduler (`make heartbeat`)

(part of Baxter — see [architecture map](../../CLAUDE.md))

Baxter can act on a schedule, unprompted. **`make heartbeat`** runs **one dedicated driver** (`scripts/heartbeat.ts`, a `poll.ts`-style node loop, same image/tokens/config-volume, on the shared network) that every ~minute fires **due tasks** from a shared `~/.mail-agent/schedule/schedule.json` and delivers the result to Discord, email, or SMS (a phone number, or a previously received SMS group via `sms-cli send-group`). From normal email/Discord runs, Baxter controls ordinary tasks via **`schedule-cli`** (`add`/`cancel`/`list`, plus the read-only `groups` discovery verb for SMS-group targets) and runtime-owned tasks via `schedule-cli system list`, `schedule-cli system enable <key>`, and `schedule-cli system disable <key>`; system tasks cannot be added or cancelled. The shim + `Bash(schedule-cli *)` grant ride the email/Discord grant sets (so a voice-dispatched run, which reuses `DISCORD_TOOLS`, has it too); a heartbeat-fired run is deliberately **not** granted `schedule-cli` (a scheduled task can't modify tasks). The surfaces' tool allow-lists differ (mail: mail + schedule-cli; discord: discord + schedule-cli — reused as-is by voice-dispatch; heartbeat: mail + discord + sms, but *not* schedule-cli) — and rather than hand-synced per-daemon `ALLOWED_TOOLS` strings, they're now **composed from a shared core in `scripts/grants.ts`** (`MAIL_TOOLS`/`DISCORD_TOOLS`/`HEARTBEAT_TOOLS`). **The tool grants stay per-surface (the enforced boundary); the skill docs come from one base list each surface filters.** `grants.ts` defines a single base `SKILL_NAMES`, and each surface's `*_SKILL_NAMES` is `skillNamesExcept(...its exclusions...)` (its `*_SKILL_SRCS` derive from those names): mail excludes `discord`, heartbeat excludes `schedule`, discord/voice exclude nothing. `BAKED_SKILL_NAMES` (the learned-skill shadow-guard floor) is the base list's names (each surface is a subset, so their union is the base). A staged skill *doc* never grants a *tool*: each skill exclusion mirrors a missing tool (heartbeat has neither the `schedule` doc nor `schedule-cli`; mail neither `discord` doc nor `discord-cli`), and the fail-closed `HEARTBEAT_TOOLS` (no `schedule-cli`), not the doc absence, is what actually prevents a scheduled task from scheduling. So the "keep the allow-rule sources in sync" hazard is gone: one tool source of truth per surface, one base skill list, and the guard can't drift from what the daemons stage.

- **`scripts/schedule-store.ts`** — the store: pure queue helpers (`selectDue`, `applyClaim`→task|null, `applyOnSuccess`/`applyOnFailure`, `resolveNextRun` via `cron-parser` + an `Intl` wall-time-in-zone conversion, `cronMinGapMinutes`) **plus** locked/atomic I/O (`mutate` = `proper-lockfile` + temp-file `rename`; the lock is held only for the brief read-modify-write, never across a fire) and the log helpers. `envInt` fails **closed** on a bad numeric env var.
- **Queue semantics (SQS-style):** due = `next_run_at ≤ now && visible`. Claim sets a **15-min invisibility window** and returns the task or `null` (a concurrent `cancel` wins — the driver fires only a non-null claim). Success removes a one-shot / reschedules a cron; a **hard** failure retries after the window and gives up after `HEARTBEAT_MAX_ATTEMPTS`; an **out-of-tokens** run leaves the claim and pauses the tick (no attempt burned — a global outage isn't the task's fault). Completed, hard-failed, and gave-up outcomes append a line to `task-log.jsonl`; cap deferral emits at most one `skipped` entry per UTC day while other deferred occurrences receive no entry, and out-of-token attempts remain unlogged.
- **Enforced limits (code, not prompt):** min 1-hour recurrence for `--cron` (validated over the next 100 occurrences, no wall-clock cap; one-shot `--at` any time), `HEARTBEAT_MAX_TASKS`, and a daily `HEARTBEAT_MAX_FIRES_PER_DAY` cap enforced by the durable agent-run quota reservation below (not by counting log lines). These bound the persistence a prompt-injected `schedule-cli add` could otherwise turn into unbounded autonomous runs.
- **System tasks (runtime-owned):** a compile-time registry (`scripts/system-tasks.ts`, `SYSTEM_TASKS`) defines tasks the *runtime* — not a prompted run — executes for the household. The registered keys are `daily-calendar-digest`, `friday-weekend-check-in`, and `monday-weekly-check-in`. They persist as canonical records under the reserved `system:` id namespace in `schedule.json` (every id-minting path refuses that prefix) and are **enable/disable-only**: `schedule-cli system list`, `schedule-cli system enable <key>`, or `schedule-cli system disable <key>` — never `add`ed or `cancel`ed, and the heartbeat-fired surface still gets no `schedule-cli`. `system.enabled` is a strict boolean — a non-literal value (the string `'true'`, a number, null) is repaired to `false` and never fires. A reconciliation gate (the exported `runReconcileGate` helper, run once at startup and at the top of **every** tick, always before due selection) creates, repairs, and duplicate-collapses each registered record inside one store transaction. Any reserved-namespace collision — an ordinary record under a `system:` id, an unknown `system:*` id, wrong-key metadata, or a mixed ordinary/system duplicate set — **fails closed**: nothing is selected, claimed, or dispatched until the operator repairs it (rename the record's id to a non-reserved one, or `cancel` it when unambiguous; the runtime never renames/deletes/bypasses it itself). A newly created or repaired record's `next_run_at` comes from the definition's **own cron** through a tz-aware catch-up anchor: the most recent occurrence at-or-before *now* when it falls on today's local day (today's already-passed run lands due now), otherwise the next occurrence strictly after *now*.
- **Agent-run quota (`fire-quota.json`):** the daily `HEARTBEAT_MAX_FIRES_PER_DAY` cap is a durable UTC-date reservation file beside `schedule.json` (its own lock — reservation never runs inside a store transaction). First use seeds the window once from today's legacy log fires; after that only the reservation state counts, and UTC-day rollovers reset it empty without re-seeding. Every actual model invocation reserves its own slot immediately before that invocation, bound to the firing task's id. Ordinary prompted fires still defer the occurrence when denied. The three runtime-owned check-ins instead use deterministic per-contact fallback: quota denial stops later reservation attempts for that invocation but completes one delivery chain for every snapshotted contact. Out-of-tokens releases that contact's slot and has the same stop-and-fallback behavior. Fires that never touch a model (including a no-event digest and a zero-recipient check-in) never reserve. Log entries carry an audit-only `agent_run` flag (and `system_key` for system fires).
- **Here’s what’s on the calendar** (`daily-calendar-digest`): at 08:00 household time (one shared tz resolver: valid `BAXTER_TZ` → valid `HEARTBEAT_TZ` → `America/Los_Angeles`) the handler refreshes the household calendars and selects today's remaining/ongoing/all-day events. Zero qualifying events remains a successful zero-reservation, zero-model, zero-delivery short circuit. Otherwise it snapshots resolved recipients and performs one content-suppressed, tool-less generation plus one SMS-first/same-contact-email delivery chain per contact, in deterministic order. Runtime adds the cleaned-name greeting and uses a bounded sanitized-calendar fallback only for the affected contact. Email fallback uses the date-bearing subject `What’s on the calendar today — <local date>`.
- **Weekly household check-ins:** Friday at 09:00 receives the bounded upcoming Saturday/Sunday calendar projection; Monday at 09:00 receives no calendar data. Each resolved contact gets a separate content-suppressed, tool-less model invocation and reservation. Every prompt receives only that contact's cleaned display name (or null), at most 20 other cleaned household names plus an omitted count, and the same memory-first durable-knowledge snapshot: up to 96 KiB of shared memory, then visible Collection Markdown at up to 16 KiB each within the 128 KiB aggregate cap (private `<comment>` blocks stripped). The model chooses relevant facts while preserving every named fact's owner. Runtime owns the greeting and one per-contact SMS-first/same-contact-email chain. Validation and model failures fall back only for the affected contact, then generation continues for later contacts; quota denial or out-of-tokens also stops all remaining model attempts while every remaining delivery chain uses fallback. Diagnostics and model metadata are aggregate/index-based and structurally omit contact phone/email fields and message content. Duplicate prevention is in-process only: an unhandled interruption retains heartbeat's existing failure/retry semantics and a later invocation may restart at contact zero because there is no durable per-recipient completion state. Full designs: `docs/superpowers/specs/2026-08-20-system-scheduled-tasks-design.md`, the baxter-control `2026-08-21-weekly-household-check-ins-design.md`, and `docs/superpowers/specs/2026-08-21-per-recipient-system-check-ins-design.md`.
- **Timezone** is the requester's: Baxter sets `--tz` from what they state/known, asking if a clock-time task needs it; `HEARTBEAT_TZ` is only the fallback. The driver writes `DISCORD_TOKEN_PATH` (0600) at startup like `discord-bot.ts` and strips the token from fired runs' env. Full design: `docs/superpowers/specs/2026-07-15-baxter-heartbeat-scheduler-design.md`.
