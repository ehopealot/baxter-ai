# Tool CLIs: files-cli, collections-cli, memory-cli, calendar-cli, checklist-cli, recipes-cli, link-cli, data-cli, skills-cli

(part of Baxter — see [architecture map](../../CLAUDE.md))

These are Baxter's workspace/data/discovery tool CLIs, the credential-less scoped boundaries alongside the browsers and [remote code execution](code-executor.md).

**`files-cli` (`scripts/files-cli.ts`).** The run's read-only window into its **own workspace** — `files-cli list [subpath]` (sorted files + sizes), `files-cli grep [-i] <pattern> [subpath]` (fixed-string content search, `file:line: match`), and `files-cli search [-n N] [--paths-only] [--sub <path>] <query...>` (BM25-ranked relevance search over markdown-heading-chunked files — best matches first with the section heading + a snippet; same confined walk + caps as `grep`, no persistent index). It exists because the run is granted **no** `ls`/`grep`/`find` (bare Bash isn't allowlisted) and Claude Code's native `Grep`/`Glob` aren't granted either, yet the run's durable files (memory, per-channel notes, learned skills, saved scripts, artifacts) all live in `MEMORY_DIR` and it otherwise has no way to enumerate or search them — only the exact paths the prompt injects. **The confinement is the security point, not a UX detail:** unlike Claude Code's native `Grep`/`Read` on the **claude harness** (which aren't cwd-bounded — the run's `Read` can open the token files there, the harness-specific residual detailed in [Auth](security.md); the structured-tool harnesses' `read_file` IS cwd-bounded, so this doesn't apply to the deployed openrouter config), `files-cli` resolves every path against `MEMORY_DIR` and refuses anything that escapes it after symlink resolution (and the walk never follows symlinks), so it **cannot** reach the mail/discord key files, which live one level up in `~/.mail-agent/` (the *parent* of `memory-workspace/`). So it adds discovery/search over what the run can already read, without widening the reach a filesystem-wide native search would. `grep` is deliberately fixed-string, and `search` tokenizes rather than building a `RegExp` (no regex on a model-supplied query → no ReDoS; `code-cli` covers regex); output is capped. `search` is the ranked-retrieval complement to `grep`'s exact-string match, for when the run doesn't recall the exact words — see `docs/superpowers/specs/2026-07-27-memory-search-design.md` (Phase 2, an opt-in embedding reranker, is specified there but not built). No skill — it's documented inline in each prompt's "stay in your working directory" note; the shim is on PATH via `app/Dockerfile`, and every surface grants `Bash(files-cli *)`. **`files-cli lru [subpath] [-n N] [--newest]`** is a fourth verb for **cleanup**: it lists workspace files sorted by last use (oldest first — the stalest at the top), joining the filesystem `mtime` (authoritative last-*write*, whatever wrote it) with an append-only **access log** (`scripts/access-log.ts`, `ACCESS_LOG_PATH` in `STATE_DIR`) that records last-*read*/last-write per path. The log is written by the structured harness's `read_file`/`write_file`/`edit_file` (`harnesses/openrouter-tools.ts`) — the cwd-confined choke point for the agent's file access — keyed by `MEMORY_DIR`-relative path, one lock-free JSONL append per op (best-effort; a failed append never breaks the file op), folded on read and compacted past a cap. It's in `STATE_DIR` (not `MEMORY_DIR`) so it isn't itself a tracked file and the run can't tamper with it. **Coverage caveat:** the read-tracking sees the structured harnesses (openrouter/openai/custom) only — the opt-in **`claude`** harness's native `Read`/`Write` bypass our code, so for those runs `lru` falls back to `mtime` alone (writes still land; reads don't).

**`collections-cli` (`scripts/collections-cli.ts`).** Category-oriented **Collection** documents — one `<slug>.md` file per Collection under `COLLECTIONS_DIR` (`MEMORY_DIR/collections/`), shared across every surface through `MEMORY_DIR`. The file contents are a strict JSON list of `{title, content, notes}` strings. Each object is one real item in that Collection's category (a place, person, recommendation, or another independently useful unit), not a Markdown list of peer items. `title` and freeform Markdown `content` are family-visible; `notes` is required per item but Baxter-only internal context. A Markdown list remains valid when every bullet is a detail of its one entry; peer items become separate objects. `make` seeds `[]`, and `save` validates the complete JSON list before its CAS write. Legacy non-JSON source remains listable/openable so Baxter can replace it naturally on a later whole-file save, but Home omits it. Five verbs: `list`, `make <name>` (create-only, `wx` flag → errors on a duplicate slug so notes can't be clobbered), `open <slug>` (prints the whole file), `save <slug> --expect <version>` (replaces the **whole** file from stdin — a mistyped slug errors with "make it first" rather than upserting a stray Collection; the prompts/skill tell Baxter to `list` first and to send the full file each save, and to ask after returning a list of options whether the user wants the results added to a new or existing Collection rather than adding them unprompted; lists of steps, tasks, ingredients, and checklist items are excluded), and `delete <slug> --expect <version>` (removes the whole Collection only after a locked re-read confirms the version it opened). Writes are **atomic** (temp sibling + `rename`), so a concurrent `open` never sees a half-written file. **Concurrent saves and deletes of the same collection are guarded by optimistic concurrency (compare-and-swap):** `open`/`make`/`save` vend an 8-hex `version:` token (first 8 hex of sha256 over the file's raw bytes, via the shared `versionToken(buf)`; emitted on **stderr**), and `save --expect <version>` is **rejected** if the file changed since that version — the reject message deliberately echoes only the *stale supplied* token, never the current one (handing back the valid token would let a stale body pass). A brief `proper-lockfile` lock (mirroring `schedule-store.mutate`) wraps the read→compare→rename-or-unlink critical section so a stale save or delete cannot win after a newer mutation; its current-source read uses the shared descriptor fence, so an out-of-band oversized, symlinked, or growing file is rejected before the CAS token comparison. This closes the old last-write-wins lost-update window. The CAS core (`versionToken` + locked read→compare→atomic mutation) is now **extracted to `scripts/cas-file.ts`** and shared with `memory-cli` (below), which closes the same window on the shared `memory.md`/`CREDENTIALS.md` — the per-channel Discord notes stay on native `Edit` (the dispatcher largely serializes them). The deletion extension is designed in `docs/superpowers/specs/2026-08-29-collections-cas-delete-design.md`. On the claude harness a too-large `open` body can be sidestepped for just the token via `open <slug> 2>&1 >/dev/null` (the skill documents it). Names slugify to `[a-z0-9-]` (length-capped, `basename`-defended) and paths resolve under `COLLECTIONS_DIR` — like `files-cli`, it can't escape the workspace. It's a **shared-core CLI** (`Bash(collections-cli *)` is in `grants.ts`'s `CORE_TOOLS`, so every surface grants it, and `collections` is in each surface's `SKILL_SRCS` → `BAKED_SKILL_NAMES`); shim on PATH via `app/Dockerfile`; the `collections` skill (`skills/collections/SKILL.md`) carries the full command reference. **Preamble injection:** every run (email, Discord, and heartbeat) gets the current collection list in its prompt via `collectionsPreamble()` → a `{{COLLECTIONS_LIST}}` slot, so a run sees what exists without a `list` call and is nudged to open/update/create. It emits **slug + last-updated date only** — deliberately NOT the free-text title/body, which is indirectly attacker-influenced; slugs are `[a-z0-9-]`-confined and dates numeric, so the injected block can't smuggle an instruction into every future preamble (the title/body a run reads on demand via `open`, never auto-injected). Capped at 40 (the most-recently-updated kept, so an active collection isn't buried by the alphabetical head) with an "…and N more" tail; the preamble path passes `listCollections(..., { withTitles: false })` to skip the per-file title read on every render.

**`memory-cli` (`scripts/memory-cli.ts`).** CAS-protected writes to the **shared memory files** — `memory.md` and `CREDENTIALS.md` under `MEMORY_DIR`, written by *every* surface's run. Native `Write`/`Edit` on these left a last-write-wins window (two runs read, then whole-file write, and the second clobbers the first); `memory-cli` closes it with the same compare-and-swap as `collections-cli`, via the shared `cas-file.ts`. Three verbs over a **fixed target allowlist** (`memory` | `credentials` — never an arbitrary path, so no traversal, same `MEMORY_DIR` confinement as `files-cli`): `read [target]` (prints the file, vends its `version:` on **stderr**; a not-yet-written file reads as empty with the empty-buffer token, so it's create-on-first-write), `write <target> --expect <version>` (whole-file CAS, same reject-without-echoing-the-current-token semantics as `collections-cli save`), and **`append <target>`** — the lock-serialized, **token-free** path for the dominant "record a fact / add a login" op: because the append re-reads the current bytes *inside* the lock, two concurrent appends both survive (lossless), an empty append is a no-op, and a single `\n` boundary is inserted when needed. `append` is deliberately the zero-friction default while revision costs a `read`→`write --expect` loop, so the prompts pair it with a **keep-it-curated** nudge (fold appends into the right section; don't let `memory.md` — injected into every run — become an append log). Shared-core CLI (`Bash(memory-cli *)` in `CORE_TOOLS`; `memory` in `SKILL_NAMES` → every surface); shim on PATH via `app/Dockerfile`; the `memory` skill carries the reference. The prompts route memory writes here instead of native `Write`/`Edit`; a stray native write still bypasses the lock (an accepted, documented residual — strictly better than the pre-CLI nudge-only state). Design: `docs/superpowers/specs/2026-07-30-memory-cli-cas-design.md`.

**`calendar-cli` (`scripts/calendar-cli.ts` + `scripts/ical.ts` + `scripts/calendar-store.ts`).** Baxter's calendar, for the family-ops service. It **reads** the family's calendar (`poll` fetches the feed(s) listed in `calendar/feeds.json` — managed via the home settings UI (Settings -> Calendar feeds) and pushed live by the home Durable Object, rather than an env var — a Google secret-iCal / iCloud / any ICS link — caps + time-boxes like `web-cli`, parses to a cache; a bad feed is reported not fatal, and a total outage keeps the previous cache rather than wiping it). `add`/`remove`/`list` manage Baxter's own events in `STATE_DIR/calendar/events.json` (not `MEMORY_DIR`, so `calendar-cli` is the only writer and the `proper-lockfile` `mutate` gates writes); `agenda [--days N]` shows a merged upcoming view (own ∪ family, source-tagged); `ics <uid>` emits a single-event ICS for an attachment. After creating an own event for an email or direct-SMS reply, `get-add-to-calendar-link <uid>` signs Home issuance and prints exactly the Google then device lines, each a distinct bare `/a/<10-character-case-sensitive-base62-code>` URL. The strict issuer response never exposes a tenant or legacy token; the command has no recipient/provider flags or preference store. New immutable, unauthenticated snapshots expire after three hours; a pre-change snapshot retains its stored expiry when reused. Their security/availability tradeoffs are documented in `security.md`. `ical.ts` also **parses** the family feed (`parseIcs` — unfold, TZID via the shared `tz.ts` Intl conversion, skips nested `VALARM` sub-components, tolerant per-event) + expands **scoped** recurrence (`expandInWindow` — simple DAILY/WEEKLY/MONTHLY expanded, exotic RRULE surfaced not dropped). The published subscription feed and its object-storage credential were removed; poll freshness is handled by the home calendar surface. Shared-core CLI (`Bash(calendar-cli *)` in `CORE_TOOLS`; `calendar` in `SKILL_NAMES`); shim on PATH via `app/Dockerfile`; the `calendar` skill carries the reference.

**`checklist-cli` (`scripts/checklist-cli.ts` + `scripts/checklist-store.ts`).** Checkable-item lists — groceries, packing, todos, "before the trip": items get checked off, then cleared. **Distinct from `collections-cli`:** a checklist is things you *complete* (rule of thumb the skills give the model: *can each entry be checked off? → checklist*); a collection *aggregates* notes that never get "done". Verbs: `lists`/`make <name> [--channel <id>]`/`show [--open]` (`--open` hides checked-off items, so "what's left?" reads differently from the full list)/`add <name> <item…> [--due <ISO>]`/`check`/`uncheck`/`remove`/`clear [--all]` (bare `clear` drops **checked** items, `--all` empties)/`rm`, plus **`find <phrase…>`** — a ranked fuzzy search over **open** items (reusing files-cli's `tokenize` + a token-overlap/substring score) that turns a natural "I did X" message into the item to check off; the prompts steer the model to `find`-and-check a confident match and **ask which list** when a phrase matches items across more than one. `check`/item lookup is fuzzy *within* a list and errors on an ambiguous tie rather than ticking the wrong item. Store at `STATE_DIR/checklists/checklists.json` — in `STATE_DIR`, NOT `MEMORY_DIR`, so `checklist-cli` is the sole writer and the `proper-lockfile` `mutate` gates writes (same as calendar/schedule stores). **Opt-in todo powers** (no rigid shopping/todo type): a per-item `--due` is paired with an agent-scheduled **self-cancelling** reminder (`schedule-cli` task phrased "remind only if still open", so completing/removing early no-ops it — no CLI-tracked task id); a per-list `--channel` binds it to a Discord channel, mirrored **one message per item** (`Item.mirrorMessageId`) so a ✅ reaction maps unambiguously to one item — the two-way completion is the one piece that touches `discord-bot.ts`'s reaction dispatcher (later phase). Shared-core CLI (`Bash(checklist-cli *)` in `CORE_TOOLS`; `checklist` in `SKILL_NAMES`); shim on PATH via `app/Dockerfile`; the `checklist` skill carries the reference. The family-facing tap-to-check web page (magic-code auth) is a baxter-control follow-up. Design: `docs/superpowers/specs/2026-07-31-checklist-cli-design.md`.

**`recipes-cli` (`scripts/recipes-cli.ts` + `scripts/recipes-store.ts`).** A **step-oriented** recipe store: instead of the traditional "all ingredients up front, then a wall of prose," each step carries only the ingredients *it* uses and its own active/cook time, so `show` can present a recipe step by step. Verbs: `list` (slug/title/servings/total time/last-updated), `show <slug> [--json]` (readable step-by-step dump, or the raw JSON to edit-and-resave), `save <slug>` (recipe JSON on stdin, **validated**, create-or-replace), `rm <slug>` — no separate `validate` verb, since `save` already validates and reports before writing. Store at `STATE_DIR/recipes/` (one JSON file per recipe) — in `STATE_DIR`, NOT `MEMORY_DIR`, so `recipes-cli` is the **sole writer** and a native `Write` can't bypass its format validation (same posture as `checklist-cli`/`calendar-cli`), atomic writes (temp + rename) under a `proper-lockfile` lock. **Validation is shape-only** — required fields, non-negative-integer minutes, `servings` >= 1, non-empty title/ingredients/steps, per-field length/count caps, and (when present) an http(s)-only `source` URL — deliberately **not** cross-checking recipe-level aggregates against the per-step breakdown. The CLI **exits nonzero on any misuse or validation failure** (missing/extra args, unknown verb, unknown slug, malformed stdin JSON, an invalid recipe — which writes nothing) — the `run_cli` invariant shared by every CLI here. The `recipes-cli` core is pure fs + validation with no LLM involvement; the **`recipes` skill** (`skills/recipes/SKILL.md`) owns everything upstream and downstream of it — intake (restructuring a linked or photographed recipe into the step-oriented model, setting `source` only for a link) and presentation (walking the user through it step by step, each step's own ingredients and timing, rather than dumping the full list up front). Shared-core CLI (`Bash(recipes-cli *)` in `CORE_TOOLS`; `recipes` in `SKILL_NAMES` → every surface); shim on PATH via `app/Dockerfile`. Design: `docs/superpowers/specs/2026-08-06-recipes-cli-design.md`.

**`link-cli` (`scripts/link-cli.ts`).** A read-only resolver that turns a checklist, chat, recipe, or published Collection into its `home.bax.bot` URL, so a run can hand the family a deep link instead of describing where a thing lives. One verb shape: `link-cli <type> <name|id|slug> [--json]`, where `<type>` is `list`/`chat`/`recipe`/`collection` (singular or plural). **list** takes a *name* and resolves it fuzzily to the list's slug (reusing `checklist-cli`'s `resolveList`, which filters tombstoned lists and throws on no-match/ambiguous); **chat** takes an *id* (`wc-<n>`, shape-checked via the exported `isValidChatId` then existence-checked via `listChats()`, which already excludes `deletedAt` tombstones); **recipe** takes a *slug* (existence-checked via `readRecipe`); **collection** takes a slug or name, reads its source through the shared bounded descriptor fence, and resolves it against Home's exact bounded projection. It rejects legacy Markdown until its next JSON save and any source omitted by Home's source/payload limits, so it never emits a dead `/c/<slug>` URL. It prints the **bare URL** on stdout (`{base}/l/<slug>`, `/chats/<id>`, `/r/<slug>`, or `/c/<slug>`) for paste/clipboard, or `{type,url,slug|id,name|title}` with `--json`. The base origin is the const `https://home.bax.bot`, overridable only by the **operator** via `HOME_BASE_URL` (validated as a bare `http(s)` origin — the run's `Bash(link-cli *)` grant can't set env, so a const default is safe). It performs no network I/O and holds no credentials — it only reads the same bounded local STATE_DIR/MEMORY_DIR stores the sibling CLIs already read. Like every CLI here it **exits nonzero on misuse or an unresolved lookup** (`1` not-found/ambiguous/bad-id, `2` missing-args/unknown-type) — the `run_cli` invariant — so a run never hands out a dead link. Shared-core CLI (`Bash(link-cli *)` in `CORE_TOOLS`; `links` in `SKILL_NAMES` → every surface); shim on PATH via `app/Dockerfile`; the `links` skill (`skills/links/SKILL.md`) carries the command reference. Design: `docs/superpowers/specs/2026-08-11-link-cli-design.md`.

**`data-cli` (`scripts/data-cli.ts` + `scripts/data-sources.ts`).** A curated read-only gateway to a handful of **preferred data sources** (v1: `espn` scores/schedules, `nominatim` geocoding — both keyless), so Baxter reaches a good structured source instead of scraping the open web, and never handles an API key. `data-cli <source> <path> [--query k=v ...]`, plus `list` (sources + "preferred source per query type" routing hints) and `describe <source>` (base host, key status, and a **pointer** to that source's per-source skill). **The registry owns only the trust-critical bits** (host/auth/key + a one-line routing hint) — deliberately NOT each source's endpoint shape, which is knowledge that rots. That shape lives in a **learned skill Baxter researches, verifies live, and maintains** (`data-cli-<source>`, e.g. `data-cli-espn`): `describe` points him at it — he opens it (via the Skill tool) if it exists, else probes the API and writes it (so the next run just opens it — the learn-once property, but self-healing and verified rather than a stale baked blurb). `describe` does no filesystem lookup; it unconditionally prints the pointer + the write-one-if-missing bootstrap. Adding a source is still one registry entry in `data-sources.ts`; its shape is Baxter's to fill in. Safe because a learned skill only *suggests* a path — `buildUrl`'s host-lock still confines it, so the security boundary is in the CLI, never the skill. **The host is the security boundary**, exactly as `mail-cli.ts` confines `send` to the env-sourced recipient allowlist: the registry owns each source's `base` (scheme+host+root path); the run supplies only the path suffix + query values. `buildUrl` builds the URL by **string concat** (never the two-arg `new URL(path, base)` resolution form, which would resolve a leading `/` or `//host` *against* the base and escape it) and then asserts — authoritatively, via the exported `assertConfined` — that the resolved `origin` equals the base's and the pathname is the base path or a child of it (trailing-slash guard blocks a `…/sportsfoo` sibling of `…/sports`); a reject-list (scheme/`//`/leading-`/`/`..`/`%`-encoded traversal/`?`/`#`/backslash/control char on the raw path) is fast-fail hygiene in front of it. So a keyed source's key can only ever be sent to that source's real host — and **keyed sources use `redirect:"manual"`** (a 3xx isn't followed — an open redirect would carry a query-param token cross-origin; manual mode yields an opaque-redirect, so there's no `Location` to surface, the run just retries the canonical endpoint), while keyless sources may follow but re-assert the final origin. **Keys** live in `DATA_KEYS_PATH` (`~/.mail-agent/data-keys.json`, `0600`, keyed by each source's `auth.keyName`, read at runtime) — outside `MEMORY_DIR` like the mail/discord key files, so `files-cli` can't enumerate it and the run's env carries none; **same accepted residual** as the tokens (native `Read` by exact path is still possible under the claude harness — onboard only keys whose blast radius fits that). The key value (raw **and** both URL-encoded forms) is **scrubbed** out of all emitted output, and the auth query param is structurally redacted to `[key]` in the reported URL, so an API that echoes the request URL in an error body can't leak it. Responses are **untrusted** (treat like `web-cli`/`WebFetch` content), **capped** with a truncation marker, and time-boxed by a single `AbortController` over fetch + body read (mirrors `web-cli`). Shared-core CLI (`Bash(data-cli *)` in `CORE_TOOLS`; `data` in each surface's `SKILL_SRCS` → `BAKED_SKILL_NAMES`); shim on PATH via `app/Dockerfile`; the `data` skill (`skills/data/SKILL.md`) carries the command reference. Design: `docs/superpowers/specs/2026-07-19-data-cli-design.md`.

**`skills-cli` (`scripts/skills-cli.ts`).** A **read-only discovery** gateway into the open agent-skills ecosystem (`npx skills` / [skills.sh](https://skills.sh)), so Baxter can **find** skills and **suggest** them to the operator — installing stays a human, host-side action. The **only** verb is `find` (`skills-cli find <query> [--owner <o>] [--limit <n>]`): a host-locked `GET https://skills.sh/api/search` (the endpoint `npx skills find` uses), returning validated metadata rows `{slug, name, installs, owner, repo, url, installCommand, trusted}`. There is **deliberately no `add`/install verb** — so a prompt-injected run can't install through this CLI (the *residual* is the pre-existing web-fetch + unscoped-`Write`→`learned-skills` path, gated by the `skill-discovery` skill's explicit "never fetch/transcribe an ecosystem `SKILL.md`" prohibition + operator audit; the CLI itself adds no install capability). **Every field the operator or Baxter acts on is composed in the CLI from a strict, validated parse of the attacker-influenced registry response — never naive interpolation:** `owner` matches a GitHub-owner charset (`OWNER_RE`, ≤39, start/end alphanumeric — no flag-shaped `--x`), `repo`/`slug` match `SEG_RE` (alphanumeric first char → no leading-`-`, no dot-only `..` root-escape, ≤64); `url` (constructed `github.com/<owner>/<repo>`) and `installCommand` (`npx skills add <owner>/<repo>@<slug>`) are emitted **only** when their parts validate, else `null` + a labeled `sourceRaw` — so a hostile `source`/`id` (`; curl | sh`, backticks, `-g`, `../..`) can never reach a shell command or a flag-shaped argument the operator pastes. `trusted` is an **exact case-insensitive ASCII** match against a verified-vendor allowlist (`vercel-labs`/`vercel`/`anthropics`/`microsoft` — deliberately not `anthropic` singular; env-extensible via `SKILLS_TRUSTED_OWNERS`, validated the same way); **install counts are a weak, self-reported, gameable signal, never the trust signal or the sort key** (rows are ordered trusted-first). Host-locked exactly like `data-cli` (`buildSearchUrl` can't produce an off-origin URL — fixed `/api/search` path, run supplies only encoded query *values*; exported `assertConfined` re-checks origin+path); output is **untrusted** (metadata only, never a skill body), capped + time-boxed. The registry base is a const default overridable only by the **operator** (`SKILLS_REGISTRY_BASE`, validated as a bare `scheme://host[:port]` origin — http/https, no path/query/userinfo) — the run can't set it (env-prefix doesn't match the `Bash(skills-cli *)` grant; `run_cli` is shell-less). Shared-core CLI (`Bash(skills-cli *)` in `CORE_TOOLS`; `skill-discovery` in each surface's `SKILL_SRCS` → `BAKED_SKILL_NAMES`); shim on PATH via `app/Dockerfile`; the `skill-discovery` skill carries the trusted/untrusted "recommend vs just-print-the-command" behavior. Vetted skills are installed **baked** via **`make add-skill SKILL=owner/repo@slug [NAME=…]`** (`scripts/add-skill.ts`): it fetches with the ecosystem's own `npx skills add` into an ISOLATED temp dir (never the repo), copies the vetted dir into `app/skills/<name>/`, and appends `<name>` to the base `SKILL_NAMES` (shadow-guarded: refuses an existing baked name; `addSkillToGrants` is unit-tested since it's surgery on the security-boundary file), then runs the grants tests. Nothing goes live until the operator reviews the new SKILL.md + `git diff` and rebuilds — it only stages working-tree changes, so the fetch is automated but the vetting stays the operator's. Never into the run-writable `learned-skills/` tier, where vetting wouldn't persist. Remaining fast-follow: daemon-side logging of newly-appeared learned-skill names. Design: `docs/superpowers/specs/2026-07-21-skills-cli-discovery-design.md`.
