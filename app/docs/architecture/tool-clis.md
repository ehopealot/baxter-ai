# Tool CLIs: files-cli, projects-cli, data-cli, skills-cli

(part of Baxter — see [architecture map](../../CLAUDE.md))

These are Baxter's workspace/data/discovery tool CLIs, the credential-less scoped boundaries alongside the browsers and [code execution](codapi.md).

**`files-cli` (`scripts/files-cli.ts`).** The run's read-only window into its **own workspace** — `files-cli list [subpath]` (sorted files + sizes), `files-cli grep [-i] <pattern> [subpath]` (fixed-string content search, `file:line: match`), and `files-cli search [-n N] [--paths-only] [--sub <path>] <query...>` (BM25-ranked relevance search over markdown-heading-chunked files — best matches first with the section heading + a snippet; same confined walk + caps as `grep`, no persistent index). It exists because the run is granted **no** `ls`/`grep`/`find` (bare Bash isn't allowlisted) and Claude Code's native `Grep`/`Glob` aren't granted either, yet the run's durable files (memory, per-channel notes, learned skills, saved scripts, artifacts) all live in `MEMORY_DIR` and it otherwise has no way to enumerate or search them — only the exact paths the prompt injects. **The confinement is the security point, not a UX detail:** unlike Claude Code's native `Grep`/`Read` on the **claude harness** (which aren't cwd-bounded — the run's `Read` can open the token files there, the harness-specific residual detailed in [Auth](security.md); the structured-tool harnesses' `read_file` IS cwd-bounded, so this doesn't apply to the deployed openrouter config), `files-cli` resolves every path against `MEMORY_DIR` and refuses anything that escapes it after symlink resolution (and the walk never follows symlinks), so it **cannot** reach the agentmail/discord key files, which live one level up in `~/.mail-agent/` (the *parent* of `memory-workspace/`). So it adds discovery/search over what the run can already read, without widening the reach a filesystem-wide native search would. `grep` is deliberately fixed-string, and `search` tokenizes rather than building a `RegExp` (no regex on a model-supplied query → no ReDoS; `code-cli` covers regex); output is capped. `search` is the ranked-retrieval complement to `grep`'s exact-string match, for when the run doesn't recall the exact words — see `docs/superpowers/specs/2026-07-27-memory-search-design.md` (Phase 2, an opt-in embedding reranker, is specified there but not built). No skill — it's documented inline in each prompt's "stay in your working directory" note; the shim is on PATH via `app/Dockerfile`, and every surface grants `Bash(files-cli *)`.

**`projects-cli` (`scripts/projects-cli.ts`).** Cross-cutting **project** notes — one markdown file per project under `PROJECTS_DIR` (`MEMORY_DIR/projects/`), so a project carries context across all four surfaces (email/Discord/heartbeat/voice-dispatch, all share `MEMORY_DIR`). Four verbs: `list`, `make <name>` (create-only, `wx` flag → errors on a duplicate slug so notes can't be clobbered), `open <slug>` (prints the whole file), and `save <slug> --expect <version>` (replaces the **whole** file from stdin — a mistyped slug errors with "make it first" rather than upserting a stray project; the prompts/skill tell Baxter to `list` first and to send the full file each save). Writes are **atomic** (temp sibling + `rename`), so a concurrent `open` never sees a half-written file. **Concurrent saves of the same project are guarded by optimistic concurrency (compare-and-swap):** `open`/`make`/`save` vend an 8-hex `version:` token (first 8 hex of sha256 over the file's raw bytes, via the shared `versionToken(buf)`; emitted on **stderr**), and `save --expect <version>` is **rejected** if the file changed since that version — the reject message deliberately echoes only the *stale supplied* token, never the current one (handing back the valid token would let a stale body pass). A brief `proper-lockfile` lock (mirroring `schedule-store.mutate`) wraps the read→compare→rename critical section so two racing saves can't both pass the compare. This closes the old last-write-wins lost-update window (the shared `memory.md`/channel files still have it — they're written with native `Read`/`Write`/`Edit`, no CLI to hang a token on; the prompts now nudge `Edit`-over-`Write` there, and a future `memory-cli` would reuse this exact pattern). Design: `docs/superpowers/specs/2026-07-22-projects-cli-cas-design.md`. On the claude harness a too-large `open` body can be sidestepped for just the token via `open <slug> 2>&1 >/dev/null` (the skill documents it). Names slugify to `[a-z0-9-]` (length-capped, `basename`-defended) and paths resolve under `PROJECTS_DIR` — like `files-cli`, it can't escape the workspace. It's a **shared-core CLI** (`Bash(projects-cli *)` is in `grants.ts`'s `CORE_TOOLS`, so every surface grants it, and `projects` is in each surface's `SKILL_SRCS` → `BAKED_SKILL_NAMES`); shim on PATH via `app/Dockerfile`; the `projects` skill (`skills/projects/SKILL.md`) carries the full command reference. **Preamble injection:** every run (email, Discord, heartbeat, voice-dispatch) gets the current project list in its prompt via `projectsPreamble()` → a `{{PROJECTS_LIST}}` slot (voice builds the string inline), so a run sees what exists without a `list` call and is nudged to open/update/create. It emits **slug + last-updated date only** — deliberately NOT the free-text title/body, which is indirectly attacker-influenced; slugs are `[a-z0-9-]`-confined and dates numeric, so the injected block can't smuggle an instruction into every future preamble (the title/body a run reads on demand via `open`, never auto-injected). Capped at 40 (the most-recently-updated kept, so an active project isn't buried by the alphabetical head) with an "…and N more" tail; the preamble path passes `listProjects(..., { withTitles: false })` to skip the per-file title read on every render.

**`data-cli` (`scripts/data-cli.ts` + `scripts/data-sources.ts`).** A curated read-only gateway to a handful of **preferred data sources** (v1: `espn` scores/schedules, `nominatim` geocoding — both keyless), so Baxter reaches a good structured source instead of scraping the open web, and never handles an API key. `data-cli <source> <path> [--query k=v ...]`, plus `list` (sources + "preferred source per query type" routing hints) and `describe <source>` (base host, key status, and a **pointer** to that source's per-source skill). **The registry owns only the trust-critical bits** (host/auth/key + a one-line routing hint) — deliberately NOT each source's endpoint shape, which is knowledge that rots. That shape lives in a **learned skill Baxter researches, verifies live, and maintains** (`data-cli-<source>`, e.g. `data-cli-espn`): `describe` points him at it — he opens it (via the Skill tool) if it exists, else probes the API and writes it (so the next run just opens it — the learn-once property, but self-healing and verified rather than a stale baked blurb). `describe` does no filesystem lookup; it unconditionally prints the pointer + the write-one-if-missing bootstrap. Adding a source is still one registry entry in `data-sources.ts`; its shape is Baxter's to fill in. Safe because a learned skill only *suggests* a path — `buildUrl`'s host-lock still confines it, so the security boundary is in the CLI, never the skill. **The host is the security boundary**, exactly as `mail.ts` fixes the recipient: the registry owns each source's `base` (scheme+host+root path); the run supplies only the path suffix + query values. `buildUrl` builds the URL by **string concat** (never the two-arg `new URL(path, base)` resolution form, which would resolve a leading `/` or `//host` *against* the base and escape it) and then asserts — authoritatively, via the exported `assertConfined` — that the resolved `origin` equals the base's and the pathname is the base path or a child of it (trailing-slash guard blocks a `…/sportsfoo` sibling of `…/sports`); a reject-list (scheme/`//`/leading-`/`/`..`/`%`-encoded traversal/`?`/`#`/backslash/control char on the raw path) is fast-fail hygiene in front of it. So a keyed source's key can only ever be sent to that source's real host — and **keyed sources use `redirect:"manual"`** (a 3xx isn't followed — an open redirect would carry a query-param token cross-origin; manual mode yields an opaque-redirect, so there's no `Location` to surface, the run just retries the canonical endpoint), while keyless sources may follow but re-assert the final origin. **Keys** live in `DATA_KEYS_PATH` (`~/.mail-agent/data-keys.json`, `0600`, keyed by each source's `auth.keyName`, read at runtime) — outside `MEMORY_DIR` like the agentmail/discord key files, so `files-cli` can't enumerate it and the run's env carries none; **same accepted residual** as the tokens (native `Read` by exact path is still possible under the claude harness — onboard only keys whose blast radius fits that). The key value (raw **and** both URL-encoded forms) is **scrubbed** out of all emitted output, and the auth query param is structurally redacted to `[key]` in the reported URL, so an API that echoes the request URL in an error body can't leak it. Responses are **untrusted** (treat like `web-cli`/`WebFetch` content), **capped** with a truncation marker, and time-boxed by a single `AbortController` over fetch + body read (mirrors `web-cli`). Shared-core CLI (`Bash(data-cli *)` in `CORE_TOOLS`; `data` in each surface's `SKILL_SRCS` → `BAKED_SKILL_NAMES`); shim on PATH via `app/Dockerfile`; the `data` skill (`skills/data/SKILL.md`) carries the command reference. Design: `docs/superpowers/specs/2026-07-19-data-cli-design.md`.

**`skills-cli` (`scripts/skills-cli.ts`).** A **read-only discovery** gateway into the open agent-skills ecosystem (`npx skills` / [skills.sh](https://skills.sh)), so Baxter can **find** skills and **suggest** them to the operator — installing stays a human, host-side action. The **only** verb is `find` (`skills-cli find <query> [--owner <o>] [--limit <n>]`): a host-locked `GET https://skills.sh/api/search` (the endpoint `npx skills find` uses), returning validated metadata rows `{slug, name, installs, owner, repo, url, installCommand, trusted}`. There is **deliberately no `add`/install verb** — so a prompt-injected run can't install through this CLI (the *residual* is the pre-existing web-fetch + unscoped-`Write`→`learned-skills` path, gated by the `skill-discovery` skill's explicit "never fetch/transcribe an ecosystem `SKILL.md`" prohibition + operator audit; the CLI itself adds no install capability). **Every field the operator or Baxter acts on is composed in the CLI from a strict, validated parse of the attacker-influenced registry response — never naive interpolation:** `owner` matches a GitHub-owner charset (`OWNER_RE`, ≤39, start/end alphanumeric — no flag-shaped `--x`), `repo`/`slug` match `SEG_RE` (alphanumeric first char → no leading-`-`, no dot-only `..` root-escape, ≤64); `url` (constructed `github.com/<owner>/<repo>`) and `installCommand` (`npx skills add <owner>/<repo>@<slug>`) are emitted **only** when their parts validate, else `null` + a labeled `sourceRaw` — so a hostile `source`/`id` (`; curl | sh`, backticks, `-g`, `../..`) can never reach a shell command or a flag-shaped argument the operator pastes. `trusted` is an **exact case-insensitive ASCII** match against a verified-vendor allowlist (`vercel-labs`/`vercel`/`anthropics`/`microsoft` — deliberately not `anthropic` singular; env-extensible via `SKILLS_TRUSTED_OWNERS`, validated the same way); **install counts are a weak, self-reported, gameable signal, never the trust signal or the sort key** (rows are ordered trusted-first). Host-locked exactly like `data-cli` (`buildSearchUrl` can't produce an off-origin URL — fixed `/api/search` path, run supplies only encoded query *values*; exported `assertConfined` re-checks origin+path); output is **untrusted** (metadata only, never a skill body), capped + time-boxed. The registry base is a const default overridable only by the **operator** (`SKILLS_REGISTRY_BASE`, validated as a bare `scheme://host[:port]` origin — http/https, no path/query/userinfo) — the run can't set it (env-prefix doesn't match the `Bash(skills-cli *)` grant; `run_cli` is shell-less). Shared-core CLI (`Bash(skills-cli *)` in `CORE_TOOLS`; `skill-discovery` in each surface's `SKILL_SRCS` → `BAKED_SKILL_NAMES`); shim on PATH via `app/Dockerfile`; the `skill-discovery` skill carries the trusted/untrusted "recommend vs just-print-the-command" behavior. Vetted skills are installed **baked** via **`make add-skill SKILL=owner/repo@slug [NAME=…]`** (`scripts/add-skill.ts`): it fetches with the ecosystem's own `npx skills add` into an ISOLATED temp dir (never the repo), copies the vetted dir into `app/skills/<name>/`, and appends `<name>` to the base `SKILL_NAMES` (shadow-guarded: refuses an existing baked name; `addSkillToGrants` is unit-tested since it's surgery on the security-boundary file), then runs the grants tests. Nothing goes live until the operator reviews the new SKILL.md + `git diff` and rebuilds — it only stages working-tree changes, so the fetch is automated but the vetting stays the operator's. Never into the run-writable `learned-skills/` tier, where vetting wouldn't persist. Remaining fast-follow: daemon-side logging of newly-appeared learned-skill names. Design: `docs/superpowers/specs/2026-07-21-skills-cli-discovery-design.md`.
