# Tool CLIs: files-cli, projects-cli, memory-cli, calendar-cli, checklist-cli, data-cli, skills-cli

(part of Baxter — see [architecture map](../../CLAUDE.md))

These are Baxter's workspace/data/discovery tool CLIs, the credential-less scoped boundaries alongside the browsers and [code execution](codapi.md).

**`files-cli` (`scripts/files-cli.ts`).** The run's read-only window into its **own workspace** — `files-cli list [subpath]` (sorted files + sizes), `files-cli grep [-i] <pattern> [subpath]` (fixed-string content search, `file:line: match`), and `files-cli search [-n N] [--paths-only] [--sub <path>] <query...>` (BM25-ranked relevance search over markdown-heading-chunked files — best matches first with the section heading + a snippet; same confined walk + caps as `grep`, no persistent index). It exists because the run is granted **no** `ls`/`grep`/`find` (bare Bash isn't allowlisted) and Claude Code's native `Grep`/`Glob` aren't granted either, yet the run's durable files (memory, per-channel notes, learned skills, saved scripts, artifacts) all live in `MEMORY_DIR` and it otherwise has no way to enumerate or search them — only the exact paths the prompt injects. **The confinement is the security point, not a UX detail:** unlike Claude Code's native `Grep`/`Read` on the **claude harness** (which aren't cwd-bounded — the run's `Read` can open the token files there, the harness-specific residual detailed in [Auth](security.md); the structured-tool harnesses' `read_file` IS cwd-bounded, so this doesn't apply to the deployed openrouter config), `files-cli` resolves every path against `MEMORY_DIR` and refuses anything that escapes it after symlink resolution (and the walk never follows symlinks), so it **cannot** reach the agentmail/discord key files, which live one level up in `~/.mail-agent/` (the *parent* of `memory-workspace/`). So it adds discovery/search over what the run can already read, without widening the reach a filesystem-wide native search would. `grep` is deliberately fixed-string, and `search` tokenizes rather than building a `RegExp` (no regex on a model-supplied query → no ReDoS; `code-cli` covers regex); output is capped. `search` is the ranked-retrieval complement to `grep`'s exact-string match, for when the run doesn't recall the exact words — see `docs/superpowers/specs/2026-07-27-memory-search-design.md` (Phase 2, an opt-in embedding reranker, is specified there but not built). No skill — it's documented inline in each prompt's "stay in your working directory" note; the shim is on PATH via `app/Dockerfile`, and every surface grants `Bash(files-cli *)`. **`files-cli lru [subpath] [-n N] [--newest]`** is a fourth verb for **cleanup**: it lists workspace files sorted by last use (oldest first — the stalest at the top), joining the filesystem `mtime` (authoritative last-*write*, whatever wrote it) with an append-only **access log** (`scripts/access-log.ts`, `ACCESS_LOG_PATH` in `STATE_DIR`) that records last-*read*/last-write per path. The log is written by the structured harness's `read_file`/`write_file`/`edit_file` (`harnesses/openrouter-tools.ts`) — the cwd-confined choke point for the agent's file access — keyed by `MEMORY_DIR`-relative path, one lock-free JSONL append per op (best-effort; a failed append never breaks the file op), folded on read and compacted past a cap. It's in `STATE_DIR` (not `MEMORY_DIR`) so it isn't itself a tracked file and the run can't tamper with it. **Coverage caveat:** the read-tracking sees the structured harnesses (openrouter/openai/custom) only — the opt-in **`claude`** harness's native `Read`/`Write` bypass our code, so for those runs `lru` falls back to `mtime` alone (writes still land; reads don't).

**`projects-cli` (`scripts/projects-cli.ts`).** Cross-cutting **project** notes — one markdown file per project under `PROJECTS_DIR` (`MEMORY_DIR/projects/`), so a project carries context across all four surfaces (email/Discord/heartbeat/voice-dispatch, all share `MEMORY_DIR`). Four verbs: `list`, `make <name>` (create-only, `wx` flag → errors on a duplicate slug so notes can't be clobbered), `open <slug>` (prints the whole file), and `save <slug> --expect <version>` (replaces the **whole** file from stdin — a mistyped slug errors with "make it first" rather than upserting a stray project; the prompts/skill tell Baxter to `list` first and to send the full file each save). Writes are **atomic** (temp sibling + `rename`), so a concurrent `open` never sees a half-written file. **Concurrent saves of the same project are guarded by optimistic concurrency (compare-and-swap):** `open`/`make`/`save` vend an 8-hex `version:` token (first 8 hex of sha256 over the file's raw bytes, via the shared `versionToken(buf)`; emitted on **stderr**), and `save --expect <version>` is **rejected** if the file changed since that version — the reject message deliberately echoes only the *stale supplied* token, never the current one (handing back the valid token would let a stale body pass). A brief `proper-lockfile` lock (mirroring `schedule-store.mutate`) wraps the read→compare→rename critical section so two racing saves can't both pass the compare. This closes the old last-write-wins lost-update window. The CAS core (`versionToken` + the locked read→compare→atomic-rename) is now **extracted to `scripts/cas-file.ts`** and shared with `memory-cli` (below), which closes the same window on the shared `memory.md`/`CREDENTIALS.md` — the per-channel Discord notes stay on native `Edit` (the dispatcher largely serializes them). Design: `docs/superpowers/specs/2026-07-22-projects-cli-cas-design.md`. On the claude harness a too-large `open` body can be sidestepped for just the token via `open <slug> 2>&1 >/dev/null` (the skill documents it). Names slugify to `[a-z0-9-]` (length-capped, `basename`-defended) and paths resolve under `PROJECTS_DIR` — like `files-cli`, it can't escape the workspace. It's a **shared-core CLI** (`Bash(projects-cli *)` is in `grants.ts`'s `CORE_TOOLS`, so every surface grants it, and `projects` is in each surface's `SKILL_SRCS` → `BAKED_SKILL_NAMES`); shim on PATH via `app/Dockerfile`; the `projects` skill (`skills/projects/SKILL.md`) carries the full command reference. **Preamble injection:** every run (email, Discord, heartbeat, voice-dispatch) gets the current project list in its prompt via `projectsPreamble()` → a `{{PROJECTS_LIST}}` slot (voice builds the string inline), so a run sees what exists without a `list` call and is nudged to open/update/create. It emits **slug + last-updated date only** — deliberately NOT the free-text title/body, which is indirectly attacker-influenced; slugs are `[a-z0-9-]`-confined and dates numeric, so the injected block can't smuggle an instruction into every future preamble (the title/body a run reads on demand via `open`, never auto-injected). Capped at 40 (the most-recently-updated kept, so an active project isn't buried by the alphabetical head) with an "…and N more" tail; the preamble path passes `listProjects(..., { withTitles: false })` to skip the per-file title read on every render.

**`memory-cli` (`scripts/memory-cli.ts`).** CAS-protected writes to the **shared memory files** — `memory.md` and `CREDENTIALS.md` under `MEMORY_DIR`, written by *every* surface's run. Native `Write`/`Edit` on these left a last-write-wins window (two runs read, then whole-file write, and the second clobbers the first); `memory-cli` closes it with the same compare-and-swap as `projects-cli`, via the shared `cas-file.ts`. Three verbs over a **fixed target allowlist** (`memory` | `credentials` — never an arbitrary path, so no traversal, same `MEMORY_DIR` confinement as `files-cli`): `read [target]` (prints the file, vends its `version:` on **stderr**; a not-yet-written file reads as empty with the empty-buffer token, so it's create-on-first-write), `write <target> --expect <version>` (whole-file CAS, same reject-without-echoing-the-current-token semantics as `projects-cli save`), and **`append <target>`** — the lock-serialized, **token-free** path for the dominant "record a fact / add a login" op: because the append re-reads the current bytes *inside* the lock, two concurrent appends both survive (lossless), an empty append is a no-op, and a single `\n` boundary is inserted when needed. `append` is deliberately the zero-friction default while revision costs a `read`→`write --expect` loop, so the prompts pair it with a **keep-it-curated** nudge (fold appends into the right section; don't let `memory.md` — injected into every run — become an append log). Shared-core CLI (`Bash(memory-cli *)` in `CORE_TOOLS`; `memory` in `SKILL_NAMES` → every surface); shim on PATH via `app/Dockerfile`; the `memory` skill carries the reference. The prompts route memory writes here instead of native `Write`/`Edit`; a stray native write still bypasses the lock (an accepted, documented residual — strictly better than the pre-CLI nudge-only state). Design: `docs/superpowers/specs/2026-07-30-memory-cli-cas-design.md`.

**`calendar-cli` (`scripts/calendar-cli.ts` + `scripts/ical.ts` + `scripts/calendar-store.ts`).** Baxter's calendar, for the family-ops service. Two flows: it **reads** the family's calendar (`poll` fetches the operator-configured `CALENDAR_FEED_URL`(s) — a Google secret-iCal / iCloud / any ICS link — caps + time-boxes like `web-cli`, parses to a cache; a bad feed is reported not fatal, and a total outage keeps the previous cache rather than wiping it) and **writes** by publishing its **own** events as an ICS feed the family subscribes to once. `add`/`remove`/`list` manage the own-event store (`STATE_DIR/calendar/events.json` — in `STATE_DIR`, NOT `MEMORY_DIR`, so `calendar-cli` is the only writer and the `proper-lockfile` `mutate` actually gates writes, like `schedule-store`; stable UIDs, `add` validates ISO dates so an LLM's "tomorrow" can't poison the store); `agenda [--days N]` shows a merged upcoming view (own ∪ family, source-tagged); `publish` regenerates the ICS (`ical.ts` `buildIcs` — hand-rolled RFC 5545, tested: CRLF, 75-octet folding, TEXT escaping, DATE vs UTC DATE-TIME, stable UID) and PUTs it to S3-compatible object storage (R2/B2/S3) via `aws4fetch` SigV4, credentials in `calendar-keys.json` (`0600`, `STATE_DIR`, same posture/residual as `data-keys`); `ics <uid>` emits a single-event ICS for an email "add to calendar" attachment. `ical.ts` also **parses** the family feed (`parseIcs` — unfold, TZID via the shared `tz.ts` Intl conversion, skips nested `VALARM` sub-components, tolerant per-event) + expands **scoped** recurrence (`expandInWindow` — simple DAILY/WEEKLY/MONTHLY expanded, exotic RRULE surfaced not dropped). Keeping Baxter's feed separate from the family's calendar avoids any write credential to their Google. Freshness is a recurring `schedule-cli` job (`poll && publish` every ~30 min) plus publish-after-edit, not a new daemon. Shared-core CLI (`Bash(calendar-cli *)` in `CORE_TOOLS`; `calendar` in `SKILL_NAMES`); shim on PATH via `app/Dockerfile`; the `calendar` skill carries the reference. baxter-control provisions `CALENDAR_FEED_URL` + `calendar-keys.json` per tenant (shared bucket, own bucket-root token). Design: `docs/superpowers/specs/2026-07-30-calendar-poll-publish-design.md`.

**`checklist-cli` (`scripts/checklist-cli.ts` + `scripts/checklist-store.ts`).** Checkable-item lists — groceries, packing, todos, "before the trip": items get checked off, then cleared. **Distinct from `projects-cli`:** a checklist is things you *complete* (rule of thumb the skills give the model: *can each entry be checked off? → checklist*); a project *aggregates* notes that never get "done". Verbs: `lists`/`make <name> [--channel <id>]`/`show`/`add <name> <item…> [--due <ISO>]`/`check`/`uncheck`/`remove`/`clear [--all]` (bare `clear` drops **checked** items, `--all` empties)/`rm`, plus **`find <phrase…>`** — a ranked fuzzy search over **open** items (reusing files-cli's `tokenize` + a token-overlap/substring score) that turns a natural "I did X" message into the item to check off; the prompts steer the model to `find`-and-check a confident match and **ask which list** when a phrase matches items across more than one. `check`/item lookup is fuzzy *within* a list and errors on an ambiguous tie rather than ticking the wrong item. Store at `STATE_DIR/checklists/checklists.json` — in `STATE_DIR`, NOT `MEMORY_DIR`, so `checklist-cli` is the sole writer and the `proper-lockfile` `mutate` gates writes (same as calendar/schedule stores). **Opt-in todo powers** (no rigid shopping/todo type): a per-item `--due` is paired with an agent-scheduled **self-cancelling** reminder (`schedule-cli` task phrased "remind only if still open", so completing/removing early no-ops it — no CLI-tracked task id); a per-list `--channel` binds it to a Discord channel, mirrored **one message per item** (`Item.mirrorMessageId`) so a ✅ reaction maps unambiguously to one item — the two-way completion is the one piece that touches `discord-bot.ts`'s reaction dispatcher (later phase). Shared-core CLI (`Bash(checklist-cli *)` in `CORE_TOOLS`; `checklist` in `SKILL_NAMES`); shim on PATH via `app/Dockerfile`; the `checklist` skill carries the reference. The family-facing tap-to-check web page (magic-code auth) is a baxter-control follow-up. Design: `docs/superpowers/specs/2026-07-31-checklist-cli-design.md`.

**`data-cli` (`scripts/data-cli.ts` + `scripts/data-sources.ts`).** A curated read-only gateway to a handful of **preferred data sources** (v1: `espn` scores/schedules, `nominatim` geocoding — both keyless), so Baxter reaches a good structured source instead of scraping the open web, and never handles an API key. `data-cli <source> <path> [--query k=v ...]`, plus `list` (sources + "preferred source per query type" routing hints) and `describe <source>` (base host, key status, and a **pointer** to that source's per-source skill). **The registry owns only the trust-critical bits** (host/auth/key + a one-line routing hint) — deliberately NOT each source's endpoint shape, which is knowledge that rots. That shape lives in a **learned skill Baxter researches, verifies live, and maintains** (`data-cli-<source>`, e.g. `data-cli-espn`): `describe` points him at it — he opens it (via the Skill tool) if it exists, else probes the API and writes it (so the next run just opens it — the learn-once property, but self-healing and verified rather than a stale baked blurb). `describe` does no filesystem lookup; it unconditionally prints the pointer + the write-one-if-missing bootstrap. Adding a source is still one registry entry in `data-sources.ts`; its shape is Baxter's to fill in. Safe because a learned skill only *suggests* a path — `buildUrl`'s host-lock still confines it, so the security boundary is in the CLI, never the skill. **The host is the security boundary**, exactly as `mail.ts` confines `send` to the env-sourced recipient allowlist: the registry owns each source's `base` (scheme+host+root path); the run supplies only the path suffix + query values. `buildUrl` builds the URL by **string concat** (never the two-arg `new URL(path, base)` resolution form, which would resolve a leading `/` or `//host` *against* the base and escape it) and then asserts — authoritatively, via the exported `assertConfined` — that the resolved `origin` equals the base's and the pathname is the base path or a child of it (trailing-slash guard blocks a `…/sportsfoo` sibling of `…/sports`); a reject-list (scheme/`//`/leading-`/`/`..`/`%`-encoded traversal/`?`/`#`/backslash/control char on the raw path) is fast-fail hygiene in front of it. So a keyed source's key can only ever be sent to that source's real host — and **keyed sources use `redirect:"manual"`** (a 3xx isn't followed — an open redirect would carry a query-param token cross-origin; manual mode yields an opaque-redirect, so there's no `Location` to surface, the run just retries the canonical endpoint), while keyless sources may follow but re-assert the final origin. **Keys** live in `DATA_KEYS_PATH` (`~/.mail-agent/data-keys.json`, `0600`, keyed by each source's `auth.keyName`, read at runtime) — outside `MEMORY_DIR` like the agentmail/discord key files, so `files-cli` can't enumerate it and the run's env carries none; **same accepted residual** as the tokens (native `Read` by exact path is still possible under the claude harness — onboard only keys whose blast radius fits that). The key value (raw **and** both URL-encoded forms) is **scrubbed** out of all emitted output, and the auth query param is structurally redacted to `[key]` in the reported URL, so an API that echoes the request URL in an error body can't leak it. Responses are **untrusted** (treat like `web-cli`/`WebFetch` content), **capped** with a truncation marker, and time-boxed by a single `AbortController` over fetch + body read (mirrors `web-cli`). Shared-core CLI (`Bash(data-cli *)` in `CORE_TOOLS`; `data` in each surface's `SKILL_SRCS` → `BAKED_SKILL_NAMES`); shim on PATH via `app/Dockerfile`; the `data` skill (`skills/data/SKILL.md`) carries the command reference. Design: `docs/superpowers/specs/2026-07-19-data-cli-design.md`.

**`skills-cli` (`scripts/skills-cli.ts`).** A **read-only discovery** gateway into the open agent-skills ecosystem (`npx skills` / [skills.sh](https://skills.sh)), so Baxter can **find** skills and **suggest** them to the operator — installing stays a human, host-side action. The **only** verb is `find` (`skills-cli find <query> [--owner <o>] [--limit <n>]`): a host-locked `GET https://skills.sh/api/search` (the endpoint `npx skills find` uses), returning validated metadata rows `{slug, name, installs, owner, repo, url, installCommand, trusted}`. There is **deliberately no `add`/install verb** — so a prompt-injected run can't install through this CLI (the *residual* is the pre-existing web-fetch + unscoped-`Write`→`learned-skills` path, gated by the `skill-discovery` skill's explicit "never fetch/transcribe an ecosystem `SKILL.md`" prohibition + operator audit; the CLI itself adds no install capability). **Every field the operator or Baxter acts on is composed in the CLI from a strict, validated parse of the attacker-influenced registry response — never naive interpolation:** `owner` matches a GitHub-owner charset (`OWNER_RE`, ≤39, start/end alphanumeric — no flag-shaped `--x`), `repo`/`slug` match `SEG_RE` (alphanumeric first char → no leading-`-`, no dot-only `..` root-escape, ≤64); `url` (constructed `github.com/<owner>/<repo>`) and `installCommand` (`npx skills add <owner>/<repo>@<slug>`) are emitted **only** when their parts validate, else `null` + a labeled `sourceRaw` — so a hostile `source`/`id` (`; curl | sh`, backticks, `-g`, `../..`) can never reach a shell command or a flag-shaped argument the operator pastes. `trusted` is an **exact case-insensitive ASCII** match against a verified-vendor allowlist (`vercel-labs`/`vercel`/`anthropics`/`microsoft` — deliberately not `anthropic` singular; env-extensible via `SKILLS_TRUSTED_OWNERS`, validated the same way); **install counts are a weak, self-reported, gameable signal, never the trust signal or the sort key** (rows are ordered trusted-first). Host-locked exactly like `data-cli` (`buildSearchUrl` can't produce an off-origin URL — fixed `/api/search` path, run supplies only encoded query *values*; exported `assertConfined` re-checks origin+path); output is **untrusted** (metadata only, never a skill body), capped + time-boxed. The registry base is a const default overridable only by the **operator** (`SKILLS_REGISTRY_BASE`, validated as a bare `scheme://host[:port]` origin — http/https, no path/query/userinfo) — the run can't set it (env-prefix doesn't match the `Bash(skills-cli *)` grant; `run_cli` is shell-less). Shared-core CLI (`Bash(skills-cli *)` in `CORE_TOOLS`; `skill-discovery` in each surface's `SKILL_SRCS` → `BAKED_SKILL_NAMES`); shim on PATH via `app/Dockerfile`; the `skill-discovery` skill carries the trusted/untrusted "recommend vs just-print-the-command" behavior. Vetted skills are installed **baked** via **`make add-skill SKILL=owner/repo@slug [NAME=…]`** (`scripts/add-skill.ts`): it fetches with the ecosystem's own `npx skills add` into an ISOLATED temp dir (never the repo), copies the vetted dir into `app/skills/<name>/`, and appends `<name>` to the base `SKILL_NAMES` (shadow-guarded: refuses an existing baked name; `addSkillToGrants` is unit-tested since it's surgery on the security-boundary file), then runs the grants tests. Nothing goes live until the operator reviews the new SKILL.md + `git diff` and rebuilds — it only stages working-tree changes, so the fetch is automated but the vetting stays the operator's. Never into the run-writable `learned-skills/` tier, where vetting wouldn't persist. Remaining fast-follow: daemon-side logging of newly-appeared learned-skill names. Design: `docs/superpowers/specs/2026-07-21-skills-cli-discovery-design.md`.
