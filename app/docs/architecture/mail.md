# The mail agent

The mail surface is a Resend-backed daemon. Inbound mail travels through the Resend webhook to the Worker `/mail/inbound` endpoint, where Svix signatures are verified, the recipient is routed, and the raw webhook is placed in the Durable Object queue. A SigV4-authenticated `/mail-link` socket delivers queued payloads to the container. `scripts/mail-bot.ts` reconstructs the signed request, re-verifies it through the Resend Chat SDK adapter, and dispatches one scoped Baxter run for each allowlisted inbound thread. Accepted agent envelopes are admitted under their deterministic work ID before transcript or morning-handoff mutation; those stages are idempotent durable dispatcher receipts. There is no polling loop and no AgentMail dependency.

Provisioning is handled by `baxctl add`/`baxctl home`: for tenants with the mail surface enabled, baxctl derives `BAXTER_EMAIL` as `<id>@<domain>` from the verified `RESEND_DOMAIN`. There is no inbox-provisioning command.

## File map

- **`scripts/mail-bot.ts`** — the container daemon. It maintains the durable queue cursor and signed link, verifies inbound webhook payloads through the Resend adapter, durably admits each accepted agent envelope before cursor acknowledgement, records dead letters, and dispatches scoped runs with the thread id, body, and attachment metadata. Every successfully handled sequence that produces no run (rejected, moderated, ignored, or no-event) is first admitted in `pending-side-effects`, then reaches terminal state only through a source-typed durable completion receipt before cursor persistence and ACK. Payload validation runs inside the serialized production drain. Malformed frames and retryable webhook/admission failures establish a failed-sequence floor and force reconnect without cursor advance or ACK, preventing a higher cumulative ACK until redelivery succeeds. Every tenant-scoped work ID retains an independent FIFO outcome even when dispatcher scheduling batches it. Interrupted, transient, and rate-refused work is driven by the live earliest-attempt scheduler. If an outbox state transition cannot be persisted, one bounded in-memory transition per work ID remains scheduler-owned with capped backoff; a process restart recovers the unchanged pending/running record from disk. A permanent outcome is terminal only after the source DLQ fsync succeeds. Cursor advancement uses the shared durable-directory bootstrap, then a 0600 temp inode with file fsync, atomic rename, and parent-directory fsync before ACK; a failed parent barrier remains replay-blocking in the live process.
- **`scripts/mail-cli.ts`** — the credential boundary. `reply` and `send` use the Resend Chat SDK with provider guards; `send-calendar` sends an `.ics` attachment; `get-attachment <emailId> <filename>` mints and fetches a Resend receiving-attachment URL. The CLI is the only mail-run path allowed to hold the Resend API key. Inbound wiring makes the installed Resend adapter await the real Chat handler, and commits Chat's SQLite dedupe reservation only after that handler has durably admitted work; failure rolls it back for provider redelivery.
- **`scripts/mail-delivery-receipts.ts`** — tenant-scoped-work-ID-keyed Resend idempotency and provider acceptance receipts. Before raw send or reply reaches Resend, the CLI persists the exact JSON-safe provider payload and idempotency key with file/directory fsyncs. Each process completes and records a full-ancestry directory barrier—even for an already-existing path—before first publication, and retries the whole barrier after failure. A cross-process per-work-ID lock serializes preparation, provider acceptance, and completion so the first prepared operation is immutable. Dispatcher crash replay sends that stored payload directly, without another model run, then idempotently reconciles the outbound transcript and fsyncs completion. Provider-accepted legacy receipts follow the same transcript/completion tail.
- **`scripts/mail-transcript.ts`** — durable transcript and thread Message-ID index, used to preserve context and reply headers across runs. Inbound rows use their own work-derived receipt identity so replay cannot collide with the same work ID's outbound provider row. Before first use in each process, a nested transcript directory fsyncs its full existing ancestry before any file is published; failed barriers are not remembered and retry in full. Every appended transcript file fsync is followed by a base-directory fsync, including when the file was precreated. Thread-index replacement fsyncs the temp file before rename and its parent directory afterward.
- **`scripts/mail-state-sqlite.ts`** — per-tenant SQLite state for the Chat SDK adapter, including transactional admission-scoped deduplication and thread state.
- **`scripts/queue-admission-outbox.ts`** — the light process's single tenant-wide mail/SMS/chat ledger. Every source sequence has exactly one immutable agent-dispatch or source-named non-agent terminal record before cursor/ACK eligibility. Its first containing-directory bootstrap uses the same full-ancestry durability barrier. Nonterminal records remain lifecycle blockers through retry waiting, and each surface replays only its queue/tenant scope.
- **`scripts/home-link.ts`** — signed WebSocket transport to the Worker Durable Object.
- **`scripts/paths.ts`** — centralized paths for the mail state database, link cursor, transcript, and key material.
- **`prompt.md`** — the mail eval template. Production mail runs build their prompt inline in `mail-bot.ts`; both flows use thread ids for replies and expose on-demand attachment retrieval.

## Security and delivery boundaries

- The Worker verifies the Svix webhook before routing by recipient; the container verifies the same signed request again through the Resend adapter.
- The mail bot rejects own messages, automated messages, and senders outside the tenant allowlist/operator address. Retryable handling or durable-admission failures leave the cursor unadvanced for redelivery. Explicitly permanent failures advance only after their mail dead-letter write is durable.
- `mail-cli.ts` keeps `RESEND_API_KEY` out of model-run environments, locks the sender to `BAXTER_EMAIL`, checks recipient allowlists, sanitizes content, and enforces the daily send cap.
- Inbound attachment metadata is shown to the agent. When a multimodal model is configured (`OPENROUTER_MULTIMODAL_MODEL`), forwardable attachments (image/video/audio/PDF) are additionally attached to the run natively — `selectMailMedia` mints a short-lived signed URL per attachment and routes that one run to the multimodal model (URL-passthrough; see the harness-layer multimodal-routing note). The agent can still fetch any named attachment on demand with `mail-cli get-attachment <emailId> <filename>` (the fallback for anything not forwarded), rather than receiving arbitrary provider URLs in the prompt.
