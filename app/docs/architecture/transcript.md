# The transcript-forgery sanitization pipeline (`transcript.ts`)

(part of Baxter — see [architecture map](../../CLAUDE.md))

**`scripts/transcript.ts`** — the provider-neutral transcript-forgery sanitization pipeline (`normalizeTranscriptText`/`neutralizeStructuralMarkers`/`neutralizeDanglingSeparatorTail`/`formatThreadMessage`/`extractEmailAddress` + `TRIGGER_MARKER`/`MESSAGE_SEPARATOR`), extracted out of the old `gmail.mjs` and shared by `mail-bot.ts` and `discord-bot.ts`. `formatThreadMessage` takes a provider-neutral normalized message `{from, date, subject, text, isOwn, isAllowed}`. See the sanitization-pipeline section below.

This is the most-reviewed, most-hardened part of the codebase — a long chain of consecutive automated-review rounds (13 fix commits) found and fixed real bugs here (commits from `aad325e` through `b059964`; `git log --oneline aad325e..b059964` for the full story if you need the reasoning behind a specific piece). It was extracted verbatim out of the old `gmail.mjs` into `transcript.ts` during the mail transport migration (behavior-preserving; the one deliberate change is that `formatThreadMessage` now takes a provider-neutral normalized message and normalizes `text` itself). Read this before changing any of `TRIGGER_MARKER`, `MESSAGE_SEPARATOR`, `neutralizeStructuralMarkers`, `neutralizeDanglingSeparatorTail`, `normalizeTranscriptText`, or `formatThreadMessage`.

**The problem:** the model needs the full thread transcript (not just the triggering message) for context, but it also needs to know unambiguously which message to actually respond to — and message content is otherwise attacker-influenced (anyone who threads themselves into an allowed conversation). Positional framing ("respond to the last message") turned out to be unreliable — the trigger is chosen from `mail webhook dispatch`'s candidates by `timestamp`, not by transcript position, so a chronologically-later message (e.g. the agent's own prior reply) can legitimately follow the real trigger in the transcript.

**The design that emerged:**
- Every message in the transcript is explicitly formatted; the actual trigger gets a literal `[^ RESPOND TO THIS MESSAGE]` marker appended (not positional inference).
- Content from senders not on `ALLOWED_SENDERS` (checked per-message, not per-thread) is fully redacted — From/Date/Subject/body all replaced with `[redacted]`/`[content omitted]`, not just the body.
- The agent's own past replies are exempted from redaction via a self-applied `baxter-sent` label (applied by `mail-bot.ts` on every `reply`/`send`; inbox-side metadata an inbound message can't cause to be applied to itself) — **not** via the `From` header (spoofable). This is the unforgeable analog of Gmail's old `SENT` label. Belt-and-suspenders: the adapter also refuses to trust the agent's **own address via the allowlist**, so a forged `From: <own address>` with no `baxter-sent` label is still redacted even if the own address were (mis)listed in `ALLOWED_SENDERS`. (`formatThreadMessage` receives `isOwn`/`isAllowed` as booleans; the adapter computes them.)
- Both the marker and the separator strings are neutralized wherever they appear in real message content (a fixed-point loop, since naive single-pass replacement can reconstruct an intact separator from overlapping occurrences).
- The neutralization runs on **fully composed** message blocks, not individual fields — a body that merely starts with `---\n\n` or ends with `\n\n---` contains no complete separator on its own but combines with the template's own literal `\n\n` (or the *next* block's real separator, inserted afterward by the join) to forge one. Composition-seam bugs like this were the largest single source of review findings.
- The trigger marker itself is protected by a **random UUID placeholder** during sanitization (not a fixed string — fixed placeholders are embeddable by attacker/forwarded content) and substituted for the real marker only after sanitization completes.
- Transcript-text normalization (`normalizeTranscriptText`) folds `\r\n`/`\r`/Unicode line-break-alike characters (`LINE_SEPARATOR`/`PARAGRAPH_SEPARATOR`/`NEXT_LINE`, i.e. U+2028/U+2029/U+0085) to `\n`, and **strips invisible format characters** (`\p{Cf}` — zero-width space/joiners, LRM/RLM and bidi controls, soft hyphen, etc.) entirely, before any of the above runs — every sanitizer matches literal bytes only, and the model reading the transcript isn't a byte-exact splitter, so any character that visually reads as a line break, or that hides inside/reconstructs a structural token, is an equally valid forgery vector. This is the single place the invisible-char strip lives, so both transcript surfaces (the email transcript, built by `mail-bot.ts`'s `buildThreadOutput` passing each message through `transcript.ts`'s `formatThreadMessage`; the Discord `clean()` in `discord-bot.ts`) inherit it — they all call `normalizeTranscriptText` first. `formatThreadMessage` also normalizes `text` itself now (the old `gmail.mjs` normalized the body upstream in its MIME parser, which disappeared with the Gmail path — so a raw CRLF/U+2028 body could otherwise forge a separator).
- **Two sinks, not one**: `thread.body` (fully sanitized inside `mail-bot.ts`'s `buildThreadOutput`) and the top-level `thread.from`/`thread.subject` JSON fields (deliberately left raw in `mail-bot.ts`, since `mail-bot.ts` needs the real `from` for its own allowlist re-check) both eventually reach the prompt. `mail-bot.ts`'s `renderPrompt` sanitizes `{{FROM}}`/`{{SUBJECT}}` itself, at the point of interpolation — this was the last bug found in the chain, and it's an easy one to reintroduce if a new prompt placeholder gets added without checking whether it needs the same treatment.

**If you add a new field to the prompt template or the transcript**, ask: is this attacker-influenced text? If yes, does it need `normalizeTranscriptText` + `neutralizeStructuralMarkers` before interpolation, and could it combine with adjacent template text or a subsequent join to form a partial/seam forgery?
