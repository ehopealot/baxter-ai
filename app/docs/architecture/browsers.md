# Two browsers: playwright-cli (default) + invisible-cli (stealth)

(part of Baxter — see [architecture map](../../CLAUDE.md))

Baxter has two independent browser paths, both exposed to the run via `Bash(...)` allow-rules:

- **`playwright-cli`** (Chromium, Node) — the default for ordinary browsing. Fast to start. Its skill is generated at build by `playwright-cli install --skills` under `/app/.claude/skills/playwright-cli`.
- **`invisible-cli`** (`scripts/invisible_cli.py`, Python) — an **anti-detect** browser for sites that fingerprint/block automation (Cloudflare "Just a moment…", bot walls). Backed by [`invisible_playwright`](https://github.com/feder-cr/invisible_playwright)'s patched Firefox, whose fingerprint (navigator/GPU/canvas/fonts/audio/WebRTC/timezone) is masked at the engine level — it presents as a **Windows desktop** even though the container is Linux/arm64, and `navigator.webdriver` is `false`.

**Why invisible-cli is a separate tool, not a browser flag on playwright-cli:** the patched Firefox uses invisible_playwright's own launcher and its vendored Playwright 1.61 client/Juggler driver, not the independent Node `@playwright/cli` stack. Core pins invisible_playwright v0.8.3 at commit `cbbdda07be32c620aa3b0d2adbd2c18e8ff2213d`; the Docker build temporarily installs upstream Playwright 1.61 only to run `install-deps firefox`, then removes it. The stealth also depends on invisible_playwright's launcher (Firefox prefs + per-seed fingerprint), not just the binary. Hence a self-contained Python venv (`/opt/venv`) and a from-scratch CLI.

**invisible-cli design notes** (all learned by testing, see the wrapper's comments):
- Persistent-session **daemon + client** over a unix socket (`/tmp/invisible-cli.sock`), mirroring playwright-cli's model: `open` starts the daemon+browser, later commands reuse it, `close` ends it. Command surface mirrors playwright-cli (open/goto/snapshot/find/click/dblclick/fill/type/press/hover/select/check/uncheck/go-back/go-forward/reload/screenshot/eval/close).
- **Element refs are identical to playwright-cli**: `snapshot` calls Playwright's internal `snapshotForAI` through the pinned vendored client's `send(method, timeout_calculator, params)` seam to get `[ref=eN]` handles, resolved with `aria-ref=eN` locators.
- **No persistent Firefox profile** — the patched build reliably launches a fresh profile but crashes on the *second* launch of a populated persistent profile ("Connection closed while reading from the driver"). Instead logins persist via a `storage_state` JSON file (`~/.mail-agent/invisible-state.json` on the config volume), saved after every page-changing command and on `close`, reloaded into a fresh stealth context — the same approach as playwright-cli's `state-save`/`state-load`.
- **"Headless" is headed-under-Xvfb** (invisible_playwright spawns its own Xvfb) because true headless is itself a detection signal — hence the `xvfb` package.
- The patched Firefox (~100 MB, arm64 build published upstream) is fetched at **build** time into `/opt/invisible-cache` (`XDG_CACHE_HOME`), NOT `/home/node` — the config volume shadows `/home/node` at runtime (same reason `PLAYWRIGHT_BROWSERS_PATH` points at `/opt`).
- Fixed fingerprint **seed** + pinned locale/timezone (`en-US`/`America/Los_Angeles`, env-overridable) so Baxter presents a consistent US device without a per-launch geoip lookup.
- Only one daemon runs at a time (single socket). The `close` handler unlinks the socket *before* the seconds-long browser teardown, so a new client can't connect to the dying daemon mid-shutdown (which would hit a closing page and error) — it finds no socket and spawns a fresh daemon.
- **Hang self-recovery.** Without it, a stuck browser blocked the client until the *outer* run-harness timeout (`OPENROUTER/OPENAI_CLI_TIMEOUT_MS`, ~120s). Two distinct hang shapes, both covered: a **page that never settles** hangs the client's `recv` (bounded by `INVISIBLE_CLI_CMD_TIMEOUT`, 30s — must exceed the daemon's own 20s snapshot timeout), while a **wedged Firefox launch** hangs *before* the socket exists (the daemon binds `SOCK_PATH` only after `start_browser()`), so it's caught in `_connect` (bounded by `INVISIBLE_CLI_CONNECT_TIMEOUT`, 30s). On either, the client SIGKILLs the daemon's whole **process group** (the daemon is a session leader via `start_new_session`, so its PID — written to `/tmp/invisible-cli.pid` at startup — == its pgid, taking Firefox + Xvfb down with it) — and it kills on *every* failed post-spawn connect, not just a `recv` timeout, so a wedged launch can't leak its browser stack. Then it unlinks the socket + pidfile; for `open` it respawns fresh and retries once (the "close and reopen"). Non-`open` commands have no session to resume and return an error telling the run to `open` again. Two sharp edges the pidfile mechanism has to survive: (1) `_shutdown` only unlinks the pidfile if it *still names the departing daemon* — a fast `close`→`open` means the new daemon may already have written its own PID there, and a blind unlink would silently disable recovery for the new session; (2) the whole invocation runs under a single monotonic budget (`INVISIBLE_CLI_BUDGET`, 110s — every blocking leg capped at `min(own cap, budget left)`) so even the worst compose of hang-legs stays under the 120s outer kill and its own cleanup + error always run.

`ensureSkills()` (in `runtime.ts`, called by all three claude-spawning surfaces — poll/discord/heartbeat) copies the baked skills (one base `SKILL_NAMES` list in `grants.ts`, appended to by `make add-skill`; the build-generated `playwright-cli` one under `/app/.claude/skills` and the rest of `SKILL_NAMES` under `/app/skills`. Each surface derives its staged set by **filtering the base list by its own exclusions** (`skillNamesExcept(...)` → `MAIL_/DISCORD_/HEARTBEAT_SKILL_NAMES`, from which the staged `*_SKILL_SRCS` are derived): mail drops `discord` (no `discord-cli` tool), heartbeat drops `schedule` (no `schedule-cli` — a fired task can't schedule), discord drops nothing. The exclusions are the only skill asymmetries and each mirrors a missing tool; the tool grants, not the docs, are the enforced boundary) into `MEMORY_DIR/.claude/skills/` each run (skills resolve from cwd; refreshed so a run's unscoped `Write` can't leave them corrupt), and **also stages the agent's own learned skills** (see below). The run's `--allowedTools` grants `Bash(playwright-cli *)`, `Bash(invisible-cli *)`, `Bash(code-cli *)`, `Bash(web-cli *)` (keyless web search + fetch — `search` queries a self-hosted SearXNG JSON API for ranked results, `fetch` reads a page's text; `scripts/web-cli.ts` + the `web` skill — reaches the net from the daemon, no JS, falls back to the browsers when a page is JS-heavy), `WebSearch`/`WebFetch` (native web research; no new exfil surface — the browser CLIs already reach any URL), plus `Skill` (so the run can load a skill's full command reference, not just its one-line description).

**Learned skills — why the agent authors them outside `.claude/`:** Claude Code guards its own `.claude/` directory against writes by the spawned run (confirmed by testing: a `Write`/`Edit`, and even a Bash `>>` redirect, to `MEMORY_DIR/.claude/skills/...` is refused as an ungranted permission, while writes elsewhere in the cwd like `memory.md` succeed). So the run can't write into `.claude/skills` where its old design told it to. Instead it authors skills under `LEARNED_SKILLS_DIR` (`MEMORY_DIR/learned-skills/`, a plain dir in its writable cwd), and `ensureSkills` — running in the trusted Node daemon, which has no such guard — copies each learned-skill subdir into `.claude/skills` at the start of every run. So a skill the agent writes is discoverable on its **next** run, and (since `LEARNED_SKILLS_DIR` is under the shared `MEMORY_DIR`) is shared across all three claude-spawning surfaces (email/Discord/heartbeat — their runs share `MEMORY_DIR`). Two guardrails, since the run controls `learned-skills/` and its inputs are attacker-influenced: (1) a learned skill can **never shadow a baked one** — names in `BAKED_SKILL_NAMES` (the base `SKILL_NAMES` list) are refused, so a poisoned `learned-skills/playwright-cli` can't overwrite the real skill; (2) staging is a **sync**, not accretion — `learned-skills/` is the source of truth, so removing a rogue/stale skill there (and it's gone from `.claude/skills` on the next run) is all the cleanup needed.

## Playwright browser default

`playwright-cli` resolves its default browser from a `.playwright/` workspace folder found by walking up from its own cwd. The spawned run's cwd (`MEMORY_DIR`) never had one, so with no `--browser` flag it silently fell back to the `chrome` channel — which errors, since real Google Chrome ships no Linux arm64 build and this stack runs under Colima's arm64 VM on macOS. the mail-bot/runtime `ensurePlaywrightConfig()` writes `.playwright/cli.config.json` inside `MEMORY_DIR` pointing at the `chromium` channel (already installed by the Dockerfile's `install-browser --with-deps`, no separate install step needed) before every run, so bare `playwright-cli open` just works. It's a default, not an enforced control — see the [Sandbox](security.md) section.
