# Discord bot (second surface, same agent)

(part of Baxter — see [architecture map](../../CLAUDE.md))

Baxter also lives in Discord. It's a **separate daemon from the mail surface**, built into the same image and sharing the same config volume, so memory, skills, and per-channel state carry across the fleet's surfaces. Run it with `make discord` (its own foreground container); `make run` starts the default detached fleet **including** the Discord gateway (plus the light container — all five light surfaces mail/home/heartbeat/sms/chat — and codapi); the mail surface runs in that light container by default, and setting `BAXTER_SURFACES` only narrows the set. Unset `DISCORD_BOT_TOKEN` disables it (exits 0).

- **`scripts/discord-bot.ts`** — the gateway daemon (discord.js v14). Holds the persistent websocket, and per `messageCreate` decides whether to respond, then spawns one scoped `claude -p` run per trigger via the shared `runtime.ts` `runAgent` (same stream-json logging + out-of-tokens handling as email). The harness layer `runAgent` drives — the `claude` adapter, the structured-tool harnesses, context-blowout guards, model escalation, and multimodal routing — is documented in [the harness essay](../../scripts/harnesses/CLAUDE.md). Reads `DISCORD_BOT_TOKEN`; the spawned run does not.
- **`scripts/discord-cli.ts`** — the token-scoped Discord REST CLI (raw `fetch` to API v10, no discord.js). The **only** thing besides the gateway that touches the token; the run reaches Discord only through `Bash(discord-cli *)`, mirroring how `mail-cli.ts` is the credential boundary for email. The boundary is real, not just prompt text: `discord-bot.ts` writes the token to a 0600 file (`DISCORD_TOKEN_PATH`, outside the run's cwd) at startup and passes `runAgent` an env with `DISCORD_BOT_TOKEN` **stripped**, so the run can't echo the token out via an allowed `discord-cli` command — `discord-cli` reads it from the file (env fallback for direct use). Residual (harness-specific — see the read-primitive note in [Auth](security.md)): on the **claude harness** the run's native `Read` can open the token file by exact path (0600 doesn't stop same-UID access), enabling a `Read`→`discord-cli send`/`mail reply` exfil; on the openrouter/local harnesses (the deployed posture) all read primitives are cwd-confined and it's out of reach — same shape as `mail-keys.json`; the env-strip closes the incidental echo-via-command path, not file access. Installed on PATH as `discord-cli` (Dockerfile shim). Command surface: `whoami`, `send`, `reply`, `react`, `fetch-history`, `list-channels` (read-only discovery), `create-thread`, `send-thread`, `edit`, `delete-own` (ownership-enforced in code), `delete-any`, `pin`/`unpin`, `typing`. `delete-any` is the one moderation action that reaches other users' content: it deliberately has **no** code author-check (unlike `delete-own`) and is gated instead by Discord's own per-channel **Manage Messages** permission — the operator grants it only in the few channels where Baxter may moderate, and the DELETE of *another user's* message 403s everywhere else (deleting its own message needs no permission and works anywhere — that's `delete-own`), so the server, not prompt text, bounds where it can reach other people's messages. Editing others' messages is intentionally absent because Discord forbids it (only a message's author can edit its content), so `edit` stays own-messages-only. **No membership/role/channel-management command exists** — defense in depth beside the denied permissions. (`list-channels` is read-only channel *discovery* — `GET /users/@me/guilds` + `GET /guilds/{id}/channels` so a run can resolve a channel *name* to its id (positionals are name substrings, not guild ids), which it couldn't do before; it's not channel *management*: nothing creates, edits, reorders, or deletes channels.)
- **`discord-prompt.md`** — the per-message template (placeholders `{{PERSONA_NAME}}`/`{{BOT_USER}}`/`{{CHANNEL_ID}}`/`{{CHANNEL_KIND}}`/`{{SELF_ID}}`/`{{TRIGGER_AUTHOR}}`/`{{TRIGGER_MESSAGE_ID}}`/`{{HISTORY}}`/`{{MEMORY_PATH}}`/`{{CREDENTIALS_PATH}}`/`{{LEARNED_SKILLS_DIR}}`/`{{CHANNEL_MEMORY_PATH}}`/`{{COLLECTIONS_LIST}}`/`{{LEARNED_SKILLS_LIST}}`/`{{LOADED_SKILLS}}`).
- **`discord-reaction-prompt.md`** — the lean template for a reaction-triggered run (see "Reaction wake" below); placeholders `{{PERSONA_NAME}}`/`{{BOT_USER}}`/`{{CHANNEL_ID}}`/`{{CHANNEL_KIND}}`/`{{SELF_ID}}`/`{{REACTED_MESSAGE_ID}}`/`{{REACTED_CONTENT}}`/`{{REACTIONS}}`/`{{COLLECTIONS_LIST}}`/`{{LOADED_SKILLS}}`/`{{LEARNED_SKILLS_LIST}}`/`{{MEMORY_PATH}}`/`{{CREDENTIALS_PATH}}`/`{{CHANNEL_MEMORY_PATH}}`.
- **`skills/discord/`** — the `discord` skill, in the base `SKILL_NAMES` and so staged for **discord/heartbeat** (heartbeat may deliver to Discord); **mail excludes it** (`MAIL_SKILL_NAMES` = `skillNamesExcept("discord")`, and `MAIL_SKILL_SRCS` derive from it), mirroring its missing `discord-cli` tool — docs track the tools, and never grant them.

**Response gate** (`classifyMessage`, pure + unit-tested): the **only** hard exclusions are **our own messages** (gated by `selfId` — in the `messageCreate` handler AND defensively in `classifyMessage`, so Baxter never acts on what he posts) and **off-allowlist guilds**. Everyone else — humans **and other bots**, treated identically — resolves to `"respond"` on DM/@mention/reply-to-us, or `"prefilter"` (a pass-through candidate) otherwise. `ChannelDispatcher` debounces per channel, serializes runs within a channel, and caps global concurrency.

**Reaction wake** (`shouldHandleReaction`, pure + unit-tested): a `MessageReactionAdd` on one of Baxter's **own** messages, by **someone other than himself** (the `reactorId === selfId` guard is what stops his own 👀/⏳/✅ status churn from waking him), in an allowed guild, spawns a run via a **separate** `ReactionDispatcher` and a lean dedicated prompt (`discord-reaction-prompt.md`) that strongly biases toward no-op. It's separate from `ChannelDispatcher` (which coalesces per channel, newest-wins) so a reaction can never drop a real message trigger; it debounces per **message** (reusing the base `ChannelDispatcher` machinery via `extends`, overriding only the coalescing to accumulate a message's reactions), under its **own smaller concurrency cap** (`DISCORD_MAX_CONCURRENT_REACTION_RUNS`, default 2) — so total parallel runs are the message cap plus the reaction cap, bounded but not shared. Needs `GuildMessageReactions`/`DirectMessageReactions` intents (non-privileged — no Portal change) and `Message`/`Reaction`/`User` partials (the bot caches almost nothing, so reactions on un-cached messages would otherwise be dropped). Out-of-tokens is ignored for reaction runs — a mere reaction shouldn't trigger a notice.

**Two deliberate changes (2026-07-16, per request):**
- **Haiku pre-filter DISABLED** — the cheap yes/no gate that `"prefilter"`-class messages passed through was removed from `handleChannel`; every non-ignored message now goes straight to a full run. To re-enable, restore `runPreFilter` and gate on `decision === "prefilter"` in `handleChannel` (git history has the Haiku implementation).
- **Other bots treated like humans** — the old bot special-case (bot @mention → strict task-oriented pre-filter; plain/reply bot message ignored unless `DISCORD_TRIGGER_ON_BOTS`) is gone, along with the `DISCORD_TRIGGER_ON_BOTS` flag and the dispatcher's now-dead `fromBot` plumbing. A bot's message triggers Baxter exactly as a human's would; **only his own messages are excluded** (by id). Baxter can't loop on *himself* — self is hard-gated. **A third-party bot loop is a real exposure, and the concurrency caps do NOT bound it**: a ping-pong runs strictly *serially*, so per-channel serialization and the global concurrency cap (which bound *parallelism*) never fire, and `DISCORD_DEBOUNCE_MS` only throttles the rate. The primary code-enforced terminator is now a **per-channel hourly run budget** — `DISCORD_MAX_RUNS_PER_CHANNEL_PER_HOUR` (default 150), enforced in `ChannelDispatcher._enqueue` (over-budget triggers are *dropped*, not queued; `_recordRun` counts each start in a rolling window; per-channel, so one runaway channel doesn't starve others; `0` = unlimited). Behind it, `DISCORD_MAX_SENDS_PER_DAY` (default 2500) remains the coarse daily backstop, with the prompt's "say your piece and stop" as the earlier soft brake. The budget is the code-enforced analog of the removed pre-filter gate. The **same knob also caps the reaction dispatcher**, applied **per channel** (via `ReactionDispatcher._budgetKey`, since that dispatcher's own key is the messageId): reaction runs are no-op-biased and never hit the send cap, so without it nothing code-enforced would bound the run *count* from external reaction churn — and because `shouldHandleReaction` fires on reactions to *any* of Baxter's messages (old ones included), a per-*message* budget would let a reactor cycle across N old messages for N separate budgets, so the budget must key on the channel to bound the whole vector. The budget is enforced at **both** `_enqueue` (drop new over-budget triggers) **and** the `waiting`-queue drain (re-check + drop over-budget waiters): since a reaction's dispatch key (messageId) differs from its budget key (channelId), a burst can park many waiters under one channel budget, and an unconditional drain would run them past the cap. `_overBudget` sweeps its whole timestamp map each call, so it can't grow unbounded across transient keys.

**Context & memory:** the run gets the channel's recent history (sanitized through the same `normalizeTranscriptText`/`neutralizeStructuralMarkers` pipeline as the email transcript) plus **two memory files** — the shared `memory.md` and a per-channel `~/.mail-agent/memory-workspace/discord/<channelId>.md` (`discordChannelMemoryPath`). The prompt tells Baxter to write channel notes liberally and to **author ad-hoc skills** under `LEARNED_SKILLS_DIR` for new bots he learns (not `.claude/skills`, which is read-only to the run — see [Learned skills](browsers.md)); the daemon stages them into `.claude/skills` each run so they're available next time.

**Send cap:** `send-state.ts` has a separate Discord counter (`DISCORD_MAX_SENDS_PER_DAY`, default 2500) enforced in `discord-cli`'s `sendMessage` at the actual post (one logical send counts once even if chunked), the flood-guard analog of email's cap.

**Permissions — "anything except manage membership":** enforced twice (Discord doesn't grant it, and `discord-cli` doesn't expose it). Denied: Create Invite, Kick/Ban Members, Manage Roles, Manage Channels, Manage Guild, Administrator, Moderate Members. Everything else granted.

**Setup:** Developer Portal → New Application → Bot tab → enable the **Message Content** privileged intent → copy the token into `app/.env` → OAuth2 URL Generator (scope `bot`, tick the granted permissions above) → open the invite URL → `make discord`.
