# Home Chat agent dispatch

The Home Chat container daemon (`scripts/chat-bot.ts`) receives ordered browser intents over the signed chat link. A successful `send-message` appends the household-authored message to the locked chat transcript, then persists one immutable tenant-scoped `chat` agent-dispatch envelope in the shared queue-admission outbox. Only after that admission may the cursor advance or the link ACK the sequence.

Transcript application is retry-safe across every boundary. The queue sequence supplies the deterministic `wc-<sequence>` message ID, and `chat-transcript.ts` checks that ID while holding the message-log lock. An identical redelivery reconciles the existing row and retries the index/admission tail; changed content under the same ID is a permanent semantic conflict. Missing or deleted chats are likewise explicit poison outcomes. Storage, index, and admission failures remain retryable and leave the cursor unadvanced.

The chat dispatcher owns each admitted envelope's full lifecycle. It uses the same live earliest-attempt scheduler and bounded deferred-transition map as mail: begin, retry, success, and permanent-failure persistence errors retain one scheduler-owned transition per work ID, interrupted records are recovered at startup, and rate refusals become durable retries rather than drops. Runs return a discriminated `ChatRunOutcome`; failed and token-exhausted model runs stay retryable, and a permanent outcome becomes terminal only after the source chat DLQ write succeeds. Coalescing only batches scheduling—every work ID executes in FIFO order and retains an independent durable outcome.

Morning-handoff consumption and preparation are dispatcher-owned. The handoff ledger records the winning chat work token so a crash replay can recover only that work item's original shared-close decision. The outbox then stores the serialized claim and prepared prompt block as a surface receipt before model execution. Replay therefore neither steals another surface's winner nor repeats preparation after its receipt is durable.

Auto-title work is also part of the durable lifecycle rather than a floating post-append promise. The generated provider result is receipted before the index mutation; the index uses set-if-untitled reconciliation, then the dispatcher sends an idempotent browser change notification and records completion. A crash or transient failure at provider-result persistence, index update, or change notification resumes from the last durable stage without overwriting a concurrent title or rerunning an already-receipted provider result.

Resident deployments without the outbox injection preserve the historical append → morning close → fire-and-forget title → dispatch behavior. Durable deployments move all post-admission work under dispatcher ownership so no accepted turn is left without a retry owner.
