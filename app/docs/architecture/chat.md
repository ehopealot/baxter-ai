# Home Chat agent dispatch

The Home Chat container daemon (`scripts/chat-bot.ts`) receives ordered browser intents over the signed chat link. A successful `send-message` appends the household-authored message to the locked chat transcript, then persists one immutable tenant-scoped `chat` agent-dispatch envelope in the shared queue-admission outbox. Only after that admission may the cursor advance or the link ACK the sequence.

Transcript application is retry-safe across every boundary. The queue sequence supplies the deterministic `wc-<sequence>` message ID, and `chat-transcript.ts` checks that ID while holding the message-log lock. Transcript files, index temporaries, and their containing directory entries are fsynced before publication/ACK eligibility. An unterminated crash tail is repaired under the transcript lock (a complete row gets its newline; an incomplete row is truncated), while newline-terminated corruption is rejected rather than skipped. An identical redelivery re-fsyncs and reconciles the existing row before retrying the index/admission tail; changed content under the same ID is a permanent semantic conflict. Missing or deleted chats are likewise explicit poison outcomes. Storage, index, and admission failures remain retryable and leave the cursor unadvanced.

The link drain is serialized and failure-blocking because ACKs are cumulative. Once a lower sequence fails, already-queued higher intents are not applied or ACKed; the link reconnects and resumes only after the new connection's ascending replay reaches the drain in order.

The chat dispatcher owns each admitted envelope's full lifecycle. It uses the same live earliest-attempt scheduler and bounded deferred-transition map as mail: begin, retry, success, and permanent-failure persistence errors retain one scheduler-owned transition per work ID, interrupted records are recovered at startup, and rate refusals become durable retries rather than drops. Runs return a discriminated `ChatRunOutcome`; failed and token-exhausted model runs stay retryable, and a permanent outcome becomes terminal only after the source chat DLQ write succeeds. Scheduling is strict FIFO per chat: only the earliest nonterminal work ID may run, and a retrying/running head blocks later work until its terminal transition is durable.

Morning-handoff consumption and preparation are dispatcher-owned. Before touching the shared-close sidecar, the outbox persists the candidate occurrence, captured audience, and owning chat work ID. The handoff ledger records that winning work token so a crash replay closes from the durable candidate regardless of current schedule eligibility and can recover only that work item's original shared-close decision. The outbox then stores the serialized claim and prepared prompt block as a surface receipt before model execution. Replay therefore neither steals another surface's winner nor repeats preparation after its receipt is durable.

Auto-title work is also part of the durable lifecycle rather than a floating post-append promise. The generated provider result is receipted before the index mutation; the index uses set-if-untitled reconciliation, then the dispatcher sends an idempotent browser change notification and records completion. A crash or transient failure at provider-result persistence, index update, or change notification resumes from the last durable stage without overwriting a concurrent title or rerunning an already-receipted provider result.

Resident deployments without the outbox injection preserve the historical append → morning close → fire-and-forget title → dispatch behavior. Durable deployments move all post-admission work under dispatcher ownership so no accepted turn is left without a retry owner.
