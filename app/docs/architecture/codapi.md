# Code execution (codapi)

(part of Baxter — see [architecture map](../../CLAUDE.md))

Baxter can write and run **Python/Node code in an offline sandbox** via `code-cli` — a third surface alongside the two browsers, for computation/parsing/data work he can't do by hand. `make codapi` stands up the sandbox as a standing service; all four claude-spawning surfaces (`run`/`discord`/`heartbeat`/`voice`) join its network and grant `Bash(code-cli *)`.

**Why codapi, not Piston/Judge0 (arm64).** This stack runs under Colima's **arm64** VM on macOS. Piston and Judge0 build on `isolate` + prebuilt **amd64** language packages, which don't work here — a spike proved it: official Piston fails at `isolate`'s namespace `clone()` under emulation, and the community `otakulabz/piston-arm` has an arm64 engine but still pulls amd64 runtime packages (`qemu-x86_64: …ld-linux-x86-64.so.2` at exec). **codapi** wins because a *sandbox is a Docker image we choose*, so official arm64 bases (`python:3.12-slim`, `node:20-slim` + libs) run natively. Full rationale + the killed-Piston evidence: `docs/superpowers/specs/2026-07-14-baxter-code-execution-codapi-design.md`.

**Architecture.** `make codapi` builds two sandbox images (`app/sandboxes/{python,node}/Dockerfile`, curated libs baked in — Python `numpy`/`pandas`/`python-dateutil`/`beautifulsoup4`, Node `lodash`/`dayjs`) and the codapi server image (`app/codapi/Dockerfile`: pinned, sha256-verified codapi binary + `app/codapi/codapi.json` + sandbox defs baked in — config is **baked, not bind-mounted**, because under docker-outside-of-docker a bind-mount source must resolve on the host daemon). It runs codapi on `<project>-net` with the **docker socket** (so codapi can launch sandbox siblings) and a `TMPDIR`-matched host bind-mount (`-v $(CODAPI_TMP):$(CODAPI_TMP) -e TMPDIR=$(CODAPI_TMP)`) — codapi writes each run's code to `os.MkdirTemp` and bind-mounts it into the sandbox, and that source path must exist on the host daemon. codapi is **not privileged** (Piston would have been); each run is `docker run --rm --network none --cap-drop all --read-only --user sandbox --memory/--pids-limit` (offline, ephemeral, hardened, capped).

**`code-cli` (`scripts/code-cli.ts`).** The credential-less scoped boundary, mirroring `mail.ts`/`discord-cli`: `code-cli python|node`, program on **stdin** or `--file <path>`, raw `fetch` → `http://codapi:1313/v1/exec`. It holds no secret — it just selects the sandbox; the enforced limits are codapi's. **Input-data channel:** with `--file` (program from the file), `code-cli`'s own piped stdin is forwarded to the sandbox as a readable file named `input` (`open("input")` / `readFileSync("input")`) — the only way to get external data into the offline, workspace-blind sandbox, since codapi ignores a request `stdin` field (verified live) but does materialize every `files` entry into the sandbox cwd. Without `--file`, stdin *is* the program (no data channel). The `code` skill (`skills/code/SKILL.md`) is in every surface's `SKILL_SRCS` and in `BAKED_SKILL_NAMES` (a learned skill can't shadow it); the shim is installed on PATH by `app/Dockerfile`.

**Security posture.** Core property is **offline execution** — `network:"none"` on every run, so even a prompt-injected run can only compute and read its own output; no exfil path. The enforced maxima live in `codapi.json` (baked into the server image), because the codapi API is unauthenticated and reachable on the network other ways (e.g. Baxter's browser CLIs can `eval` a `fetch` to it) — so `code-cli` is a scoping layer, not a hard boundary, and the limits must be server-side. **The socket link is defended in stages, and Stages 1–2 are now automated box provisioning** (the `codapi-hardening` Ansible role in `baxter-control`, off by default, box-verified):

- **Stage 0 (always on)** — the codapi *server* container is `cap_drop:ALL` + `no-new-privileges` + pids/mem-capped in `compose.yaml`.
- **Stage 1 — the socket is no longer host root.** On a provisioned box, `CODAPI_DOCKER_SOCK` points codapi at a dedicated **rootless** docker daemon, so a codapi compromise yields an unprivileged user namespace, not host root.
- **Stage 2a — the sandbox kernel boundary is gVisor.** The codapi image is built with `CODAPI_RUNTIME=runsc` (a build arg the Ansible role sets in the fleet's systemd env; `codapi.json` stays `runc` for Colima/dev parity), so each run's syscalls hit gVisor's userspace kernel, not the host's.
- **Stage 2b — the socket is parameter-locked.** An `opa-docker-authz` plugin on the rootless daemon runs the vetted `app/codapi/authz/codapi-authz.rego` (default-deny; only the two capped, offline sandbox images; **runtime must be `runsc`** so a compromised codapi cannot downgrade out of gVisor).

**Residual risk (un-provisioned box / dev):** with the role off, codapi still holds the **host** docker socket (root-equivalent) and runs `runc` — a compromise *of codapi itself* reaches the host; the sandbox hardening (drop-caps/read-only/non-root/offline) is what stands between an escaped sandbox and that socket. This is the same accepted class as Piston-privileged (widely run for public Discord code bots); mitigate by turning on the hardening role and keeping codapi + the base images updated. Runbook + the box-only verification steps: [codapi-hardening-ops.md](codapi-hardening-ops.md); design in `docs/superpowers/specs/2026-07-28-codapi-sandbox-hardening-design.md`. Especially relevant once multi-tenant: the shared (rootless) docker daemon is the one axis that is NOT per-tenant isolated.

**Artifacts (media out).** Sandbox code can produce files (charts/images/PDF/audio) — Python has Pillow/matplotlib(Agg)/reportlab plus stdlib `wave`. Since the sandbox is read-only except a bounded `/tmp` **tmpfs** (added in `codapi.json`) and files there die with the ephemeral container, artifacts come back **over stdout**: a program writes to `/tmp/artifacts/`, the `emit-artifacts.sh` wrapper (the sandboxes' `run` command) base64-frames each file, and `code-cli` decodes them into `<cwd>/artifacts/`. The frames are delimited by a **random boundary** `code-cli` mints and passes in as `/sandbox/.artifact_boundary` — but that's **collision-avoidance, not authentication**: the sandbox program can read that file and forge frames, so `code-cli` treats every frame as untrusted (basename-sanitizes the name, size-checks, skips a bad one — never escaping `artifacts/` or aborting the run). Per-artifact cap 8 MB (and ~10 MB cumulative per run); `noutput` raised to 16 MB so base64 isn't truncated. `discord-cli send|reply|send-thread --file <path>` uploads a workspace file as a Discord attachment (multipart, ≤25 MB, one send). Email attachments are a deferred fast-follow. See `docs/superpowers/specs/2026-07-15-baxter-sandbox-artifacts-design.md`.
